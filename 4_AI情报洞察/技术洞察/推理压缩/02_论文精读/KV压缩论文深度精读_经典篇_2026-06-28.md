## ★★★ StreamingLLM — Attention Sink：流式推理的奠基之作

**论文**：Efficient Streaming Language Models with Attention Sinks
**ID**：arXiv:2309.17453 | Guangxuan Xiao, Yuandong Tian, Beidi Chen 等
**机构**：MIT + Meta AI
**发表**：ICLR 2024

### 问题：流式推理的内存爆炸

**背景架构**：

```
用户连续对话 → Token持续生成 → KV Cache线性增长 → GPU显存溢出
```

两个核心问题：

**① 内存线性增长**

KV Cache 大小 = `2 × num_layers × num_heads × head_dim × seq_len × batch_size × dtype_size`

- LLaMA-2-7B，4K context → ~4GB KV Cache
- 100K context → ~100GB → 单卡无法容纳

**② 窗口注意力的崩溃**

朴素的 Sliding Window Attention（只保留最近N个token的KV）看似能解决内存问题，但实验发现：

```
当序列长度超过窗口大小 → PPL（困惑度）突然爆炸 → 生成质量崩溃
```

### 核心发现：Attention Sink 现象

**关键观察**：即使初始token（如`<s>`系统标记）在语义上不重要，softmax函数也会强制将大量注意力分数分配给它们。

```
Softmax 的数学性质：
  - softmax 必须将所有 logit 归一化为概率分布
  - 当大多数 token 与当前 query 无关时，多余的"注意力预算"被倾倒到初始 token 上
  - 这些初始 token 充当了"注意力池"（Attention Sink）
```

**实验证据**：

| 现象 | 说明 |
|------|------|
| 初始token注意力异常高 | 即使是`<s>`等无语义token也获得>0.3的注意力分数 |
| 移除初始token → PPL爆炸 | Window Attention 移除初始token后，PPL从~10跳到>1000 |
| 保留初始token → 稳定 | 仅保留前4个token + 最近窗口，PPL保持稳定 |

### StreamingLLM 方案

```
保留的KV = [前 k 个 Sink Token] + [最近 W 个 Token]
丢弃的KV = 中间的所有token
```

- **k**（Sink大小）：通常4个token
- **W**（窗口大小）：根据显存预算设定，如1024-8192

**优势**：O(W+k) 固定内存，不受序列长度影响；无需微调

### 关键数据

| 指标 | 结果 |
|------|------|
| 最大序列长度 | **4,000,000+ tokens**（LLaMA-2/MPT/Falcon/Pythia）|
| vs Sliding Window Recomputation | **22.2× 加速** |
| 内存占用 | O(1)，与序列长度无关 |
| PPL 稳定性 | 4M token 内 PPL 完全平稳 |

### 局限与产业意义

**局限**：
- 固定策略，**无法回忆中间被丢弃的token**（无检索能力）
- 仅适用于流式场景（对话/续写），不适用于需要全局理解的任务
- Sink机制是softmax病态的workaround，非principled解决方案

**产业意义**：
- 第一个实现**无限长度稳定生成**的框架
- 被vLLM/SGLang/TGI等推理框架广泛集成
- 确立了"Sink + Window"范式，后续所有KV压缩方法都需考虑Sink token

## ★★★ H2O — Heavy-Hitter Oracle：KV驱逐的范式确立

**论文**：H₂O: Heavy-Hitter Oracle for Efficient Generative Inference of Large Language Models
**ID**：arXiv:2306.14048 | Zhenyu Zhang, Ying Sheng, Tianyi Zhou 等
**机构**：斯坦福 + UC Berkeley 等
**发表**：NeurIPS 2023

### 问题：哪些KV该留？——KV压缩的决策难题

**背景**：

```
KV Cache 占用 70%+ GPU显存（长序列场景）
→ 需要丢弃"不重要"的KV
→ 但如何判断哪些KV重要？
```

**StreamingLLM的不足**：
- 只保留Sink + Recent，完全忽略了中间可能重要的语义token
- 例：长文档问答中，答案相关的token可能在文档中间

### 核心发现：Heavy Hitter 现象

**观察**：在注意力计算中，少量token贡献了大部分注意力分数值。

```
所有token的注意力分数分布：
  Top 20% token → 贡献 >95% 的注意力总值
  其余 80% token → 几乎不被关注
```

**Heavy Hitter的特征**：
- 与token在文本中的**高频共现**强相关
- 在不同query下表现稳定（不是query-dependent的）
- 移除后导致显著性能下降（证明其重要性）

### H2O 方案：动态子模优化驱逐

**驱逐策略**：

```
每次生成新token后：
  1. 计算所有缓存token的累积注意力分数
  2. 保留：Recent Token（最近ρ个）+ Heavy Hitter（分数最高的k-ρ个）
  3. 驱逐：分数最低的非Recent token
```

**理论保证**：
- 将KV驱逐形式化为**动态子模优化问题**
- 证明在温和假设下，贪心驱逐策略具有(1-1/e)的近似比
- 为后续所有KV驱逐方法提供理论基础

### 关键数据

| 指标 | 结果 |
|------|------|
| KV保留比例 | **20%**（80%内存节省）|
| vs DeepSpeed Zero-Inference | **29× 吞吐量** |
| vs FlexGen | **3× 吞吐量** |
| 延迟降低 | **1.9×**（同batch size）|
| 精度损失 | 极小（多任务评估）|

### 核心挑战对比

| 方法 | 策略 | 可回忆中间token？ | 理论保证？ |
|------|------|:---:|:---:|
| Window Attention | 只保留Recent | ❌ | ❌ |
| StreamingLLM | Sink + Recent | ❌ | ❌ |
| **H2O** | **Recent + Heavy Hitter** | **✅ 部分** | **✅ 子模优化** |

### 局限与产业意义

**局限**：
- 驱逐**不可逆**——一旦token被丢弃，永远无法恢复
- Needle-in-Haystack任务中，稀有但关键的token可能被误驱逐
- 20%预算是启发式设定，无layer/head级别的自适应分配

**产业意义**：
- 确立了"**注意力分数驱动驱逐**"范式，被后续SnapKV/PyramidKV/R-KV等广泛沿用
- 第一个提供理论保证的KV驱逐方法
- 被DeepSpeed-Inference等框架集成

## ★★★ SnapKV — 观察窗口：Prefill阶段一步压缩

**论文**：SnapKV: LLM Knows What You are Looking for Before Generation
**ID**：arXiv:2404.14469 | Yuhong Li, Yingbing Huang, Bowen Yang 等
**机构**：UC Berkeley + 商汤研究院
**发表**：NeurIPS 2024

### 问题：在线驱逐的持续开销与噪声

**H2O的问题**：

```
H2O 在每个decode step 都执行：
  1. 计算注意力分数 → 判断重要性 → 驱逐
  2. 这引入了持续的计算开销
  3. 单步注意力分数有噪声 → 可能做出错误的驱逐决策
```

### 核心发现：注意力模式的稳定性

**观察**：每个注意力头在生成过程中**持续关注相同的prompt位置**。

```
实验发现：
  - 对prompt最后几个token（"观察窗口"）计算注意力
  - 这些注意力分数揭示了每个head关注的prompt位置
  - 这个模式在后续生成中保持稳定
  - → 可以在prefill阶段就预判哪些KV重要
```

### SnapKV 方案：Prefill阶段一步压缩

```
Prefill阶段：
  1. 取prompt最后W个token作为"观察窗口"（通常32-64）
  2. 用观察窗口的attention scores → 计算每个prompt位置的"重要性分数"
  3. 对每个attention head，选取重要性最高的cluster positions
  4. 丢弃其余KV → KV Cache被压缩到目标大小

Decode阶段：
  - 无需任何驱逐操作 → 零额外开销
  - 所有计算直接在被压缩的KV上进行
```

**聚类选择**：不是选分散的top-k位置，而是选**连续的聚类区域**，保留语义连贯性。

### 关键数据

| 指标 | 结果 |
|------|------|
| 生成速度 | **3.6× 加速**（16K token） |
| 内存效率 | **8.2× 提升**（16K token） |
| 最大上下文 | **380K token**（单A100-80GB） |
| Needle-in-Haystack | 几乎无损 |
| 跨16个长序列基准 | 与全KV性能相当 |

### H2O vs SnapKV 对比

| 维度 | H2O | SnapKV |
|------|-----|--------|
| 压缩时机 | Decode每步 | **Prefill一次** |
| 决策依据 | 累积注意力（在线） | **观察窗口（离线预判）** |
| 驱逐开销 | 持续 | **零** |
| 噪声鲁棒性 | 较低（单步噪声） | **高**（稳定模式） |
| 微调需求 | 无 | **无** |

### 局限与产业意义

**局限**：
- 假设后续query与观察窗口相似——多轮对话中query可能变化
- 驱逐不可逆
- 最佳单轮长上下文场景，多轮agentic场景效果递减

**产业意义**：
- 第一个将KV压缩从"在线驱逐"转向"**预计算压缩**"
- 实现了decode阶段**零额外开销**
- 被vLLM/HuggingFace集成，生产可用

## ★★★ KIVI — K/V非对称量化：2-bit的破局

**论文**：KIVI: A Tuning-Free Asymmetric 2bit Quantization for KV Cache
**ID**：arXiv:2402.02750 | Zirui Liu, Jiayi Yuan, Hongye Jin 等
**机构**：Texas A&M + Google DeepMind 等
**发表**：ICML 2024

### 问题：KV量化的精度困境

**背景**：

```
KV Cache 占用 = seq_len × hidden_dim × 2（K+V）× batch × dtype_size

FP16 KV Cache:
  LLaMA-7B, 32K context, batch=32 → ~64GB → 无法放入单GPU

→ 量化到2-bit可减少8倍 → ~8GB
→ 但之前2-bit KV量化精度严重下降
```

**关键问题**：为什么KV的2-bit量化比weight量化难得多？

### 核心发现：Key和Value的分布差异

**深度分析揭示**：

| 维度 | Key Cache | Value Cache |
|------|-----------|-------------|
| 异常值分布 | 少数**channel**有极大值 | 少数**token**有极大值 |
| 分布形状 | 按channel分组，组内集中 | 按token分组，token间差异大 |
| 最优量化粒度 | **Per-Channel**（沿channel分组）| **Per-Token**（沿token分组） |
| 之前方法 | Per-Token（错误！）| Per-Token（正确）|

**为什么之前2-bit失败**：之前方法对K和V都用Per-Token量化。Key的异常值集中在特定channel，Per-Token量化时这些channel的异常值会拉伸整个量化范围，导致其他channel精度严重损失。

### KIVI 方案：非对称2-bit量化

```
Key Cache → Per-Channel 2-bit 量化
  - 沿channel维度分组，每个channel内独立量化
  - 异常channel不会影响其他channel
  - 每组128个channel共享一个scale和zero-point

Value Cache → Per-Token 2-bit 量化
  - 沿token维度分组，每个token独立量化
  - 异常token不影响其他token
```

**无需微调/校准**：直接在推理时在线量化，零额外训练成本。

**硬件友好实现**：分组量化 + 反量化kernel，兼容FlashAttention的内存访问模式。

### 关键数据

| 指标 | 结果 |
|------|------|
| 峰值内存（含权重） | **2.6× 降低** |
| Batch size | **4× 增大** |
| 吞吐量 | **2.35× ~ 3.47×** |
| 精度损失 | 几乎无（vs FP16）|
| 微调需求 | 无 |
| 适用模型 | LLaMA / Falcon / Mistral |

### 产业意义

- 第一个实用的**2-bit KV量化**方案
- 揭示了K/V分布的本质差异，为后续所有KV量化工作提供理论基础
- 与token驱逐方法（H2O/SnapKV等）**完全正交**，可叠加使用
- 开辟了"**量化轴**"作为KV压缩的独立维度

## ★★★ ThinK — 通道维度压缩：KV压缩的新维度

**论文**：ThinK: Thinner Key Cache by Query-Driven Pruning
**ID**：arXiv:2407.21018 | Yuhui Xu, Zhanming Jie, Hanze Dong 等
**机构**：Salesforce AI Research 等
**发表**：ICLR 2025 (Spotlight)

### 问题：Token维度压缩已到极限

**背景**：

```
已有方法都在Token维度压缩：
  H2O/SnapKV → 丢弃不重要的Token
  KIVI → 降低每个Token的精度

→ 但即使每个Token都保留，每个Token内部的channel是否都有必要？
```

### 核心发现：Channel维度的冗余

**分析发现**：

```
Key Cache 的 channel 维度存在：
  1. 不均匀的幅度分布 → 少数channel占绝大部分能量
  2. 低秩结构 → 大部分channel可被少数主成分近似
  → 这些"不重要"的channel对注意力输出贡献极小
```

### ThinK 方案：Query-Driven Channel剪枝

```
对每一步的Query：
  1. 计算每个channel对attention weight的贡献分数
  2. 剪枝贡献最小的channel（不是token，是channel！）
  3. 保留的KV Cache更"薄"（hidden_dim减小）
```

**关键创新**：
- 最小化 attention weight loss 的剪枝准则（非简单的幅度剪枝）
- Query-dependent（不同query可能保留不同的channel）
- 与token压缩方法**乘法叠加**而非竞争

### 关键数据

| 配置 | 内存节省 | Batch增大 | 精度 |
|------|---------|----------|------|
| ThinK alone vs vanilla | **>20%** | - | 维持/提升 |
| ThinK + KIVI | **2.8× 峰值内存** | **5×** | 几乎无损 |

### KV压缩维度全景

```
传统维度：
  Token维度（H2O/SnapKV）→ 丢弃不重要的Token → 竞争关系

ThinK新增：
  Channel维度 → 丢弃不重要的Channel → 乘法叠加！

组合效果：
  H2O(保留20% Token) × ThinK(保留80% Channel) × KIVI(2-bit)
  = 总压缩比 = 5 × 1.25 × 8 = 50×
```

### 局限与产业意义

**局限**：
- Channel剪枝改变tensor形状，需定制attention kernel
- Query-driven评分每步有额外开销
- 压缩比相对温和（~20%）

**产业意义**：
- 开辟了**Channel维度**作为KV压缩的新轴
- 证明了KV压缩不是零和游戏——多维度可乘法叠加
- ICLR 2025 Spotlight，学术影响力高

## ★★ DuoAttention — 头级别区分：检索头 vs 流式头

**论文**：DuoAttention: Efficient Long-Context LLM Inference with Retrieval and Streaming Heads
**ID**：arXiv:2410.10819 | Guangxuan Xiao, Jiaming Tang, Jingwei Zuo 等
**机构**：MIT-HAN-Lab
**发表**：ICLR 2025

### 问题：Token级压缩伤害检索能力

**背景**：

```
之前所有方法（H2O/SnapKV/PyramidKV）对所有attention head统一压缩
→ 但不同head有不同的功能！
→ 统一压缩导致部分head的检索能力被破坏
→ Needle-in-Haystack失败
```

### 核心发现：Retrieval Head vs Streaming Head

**关键洞察**：

| 类型 | 占比 | 功能 | KV需求 |
|------|------|------|--------|
| **Retrieval Head** | 少数（~5-20%）| 长距离检索，Needle-in-Haystack | **全量KV** |
| **Streaming Head** | 大多数（~80-95%）| 近距离+Sink | **Sink+Recent** |

**为什么之前的统一压缩会失败**：
- 对Retrieval Head做token驱逐 → 破坏了精确检索能力
- 对Streaming Head保留全量KV → 浪费（它们本来只关注Recent+Sink）

### DuoAttention 方案

```
Step 1（离线，每模型一次）：
  用合成数据 + 优化算法识别 Retrieval Head

Step 2（推理时）：
  Retrieval Head → 保留完整KV Cache
  Streaming Head → 只保留 Sink + Recent（常量长度）
```

### 关键数据

| 指标 | MHA模型 | GQA模型 |
|------|---------|---------|
| 内存降低 | **2.55×** | **1.67×** |
| Decode加速 | **2.18×** | **1.50×** |
| Prefill加速 | **1.73×** | **1.63×** |
| 最大上下文（+量化）| **3.3M token**（Llama-3-8B, 单A100）| - |

### 压缩维度升级

```
H2O:  Token级别 → 所有head统一策略
SnapKV: Token级别 → 每head独立但同维度
PyramidKV: Token + Layer级别 → 深度感知
DuoAttention: Head级别 → 检索头/流式头区分
```

### 局限与产业意义

**局限**：
- 需要离线识别Retrieval Head（合成数据优化）
- 假设head功能是静态的，跨任务可迁移
- GQA模型压缩比受限（head间共享KV）

**产业意义**：
- 解决了KV压缩的"**精度-效率悖论**"——首次同时保持检索能力和高压缩比
- 3.3M token单卡推理，工业可用
- MIT-HAN-Lab出品，与StreamingLLM同一团队

## ★★ ShadowKV — 低秩Key + Value卸载

**论文**：ShadowKV: KV Cache in Shadows for High-Throughput Long-Context LLM Inference
**ID**：arXiv:2410.21465 | Hanshi Sun, Li-Wen Chang, Wenlei Bao 等
**机构**：MIT + Intel
**发表**：ICML 2025

### 问题：CPU卸载的延迟陷阱

**背景**：

```
长上下文 → KV Cache超出GPU显存 → 卸载到CPU内存
→ 每步decode需从CPU取KV → PCIe带宽瓶颈 → 延迟暴增
→ 之前的卸载方法（FlexGen/InfiniGen）延迟负优化
```

### ShadowKV 方案：低秩Key + CPU Value

**核心思路**：Key Cache有低秩结构 → GPU上只存低秩近似；Value Cache全量放CPU。

```
GPU显存：
  Key Cache → 低秩近似（rank r << seq_len）
  → 只需存储 U(n×r) 和 S(r×d)，远小于原始K(n×d)

CPU内存：
  Value Cache → 全量存储

Decode每步：
  1. Query × 低秩Key → 快速计算近似attention scores（在GPU上）
  2. 选出top-k最重要的token
  3. 只从CPU取这k个token的完整K和V（最小化PCIe传输）
  4. 用取回的精确KV计算最终attention
```

### 关键创新

| 组件 | 传统方法 | ShadowKV |
|------|---------|----------|
| Key存储 | 全量GPU或全量CPU | **低秩近似在GPU** |
| Value存储 | 全量GPU或全量CPU | **全量在CPU** |
| 每步传输 | 全量KV或稀疏KV | **仅top-k精确KV** |
| 传输量 | O(seq_len) | **O(k)，k << seq_len** |

### 关键数据

| 指标 | 结果 |
|------|------|
| Batch size | **6× 增大** |
| 吞吐量 | **3.04×**（A100）|
| 精度 | 无损（RULER/LongBench/NIAH 6个模型验证）|
| 超越理论上限 | 甚至超过了"无限GPU显存"假设下的性能（因为减少了显存带宽压力）|

### 局限与产业意义

**局限**：
- 依赖Key的低秩假设（部分架构/层可能不成立）
- 系统复杂度高（需要PCIe带宽调优）
- 单GPU聚焦，多GPU/Tensor Parallel集成未开放

**产业意义**：
- 第一个实现**正延迟收益**的CPU卸载方案
- 开辟了"**存储层级**"作为KV压缩的新维度
- ICML 2025，工业落地价值高

## ★★ PyramidKV — 金字塔预算分配

**论文**：PyramidKV: Dynamic KV Cache Compression based on Pyramidal Information Funneling
**ID**：arXiv:2406.02069 | Zefan Cai, Yichi Zhang, Bofei Gao 等
**机构**：北京大学 + 东北大学 等
**发表**：ACL 2025 (Findings)

### 问题：均匀预算的浪费

```
H2O/SnapKV 对所有层使用相同的KV预算（如每层保留20%）
→ 但不同层的注意力模式差异巨大！

浅层：注意力广泛分散 → 需要更多KV
深层：注意力集中在少数Sink token → 只需极少KV
```

### 核心发现：金字塔信息漏斗

```
Layer 1-8（浅层）：注意力广泛分散
  → 信息从所有token汇聚 → 需要大KV预算
  → ████████████████████ 100% KV

Layer 9-24（中层）：注意力逐步集中
  → 聚焦于特定上下文 → 中等KV预算
  → ████████████░░░░░░░░ 60% KV

Layer 25-32（深层）：注意力完全集中
  → 只关注少数Sink/Critical token → 极小KV预算
  → ████░░░░░░░░░░░░░░░░ 10% KV
```

### PyramidKV 方案

```
预算分配 = 金字塔形递减

Layer 1:   budget = L_max
Layer 2:   budget = L_max - step
...
Layer N:   budget = L_min

其中：
  L_max = 较大值（如4096）
  L_min = 较小值（如64-128）
  step = (L_max - L_min) / N

每层内部：仍用注意力分数选top-k（同H2O）
关键区别：不同层的k不同
```

### 关键数据

| 指标 | 结果 |
|------|------|
| 12% KV预算 | **匹配全KV性能**（LongBench）|
| 0.7% KV预算 | **+20.5 绝对精度提升** vs 其他方法（TREC）|
| Needle-in-Haystack | LLaMA-3-70B 仅128条KV/层 → **100.0 Acc** |

### 局限与产业意义

**局限**：
- 金字塔形状是固定启发式，不随输入自适应
- 预算曲线需按模型调整
- 驱逐不可逆

**产业意义**：
- 第一个**深度感知（depth-aware）**的KV预算分配
- 揭示了注意力模式的层间结构差异
- 极端压缩比下（0.7%）仍大幅优于均匀分配

## KV Cache 压缩技术演进总结

### 压缩维度全景

```
2023: Token维度
  H2O ──────────────→ 注意力分数驱动驱逐
  StreamingLLM ─────→ Sink + Window 固定策略

2024: 量化 + 预计算
  KIVI ──────────────→ K/V非对称2-bit量化
  SnapKV ────────────→ Prefill阶段一步压缩

2024-2025: 多维度叠加
  ThinK ─────────────→ Channel维度（与Token乘法叠加）
  DuoAttention ──────→ Head维度（检索头vs流式头）
  PyramidKV ─────────→ Layer深度维度（金字塔预算）
  ShadowKV ──────────→ 存储层级维度（GPU低秩+CPU卸载）
```
