# Agent推理优化：根目标 → 瓶颈分解 → 技术选择 逻辑链

> **用途**：回答"为什么要做这7个技术"的完整逻辑链
> **适用场景**：向非技术人员解释立项依据 / 评审时说明技术优先级理由 / 自己厘清研究边界
> **性质**：本文档是"为什么"的逻辑链，具体技术方案见各课题文档

## 一、根目标（业务层）

```
【2026年业务目标】
  端到端吞吐提升 2×
  TPOT（Time Per Output Token）降低 33%
  精度损失 ≤ 1%
```

这个目标是**锚**，所有技术选择的最终评判标准是：是否服务于这三个目标。

---

## 二、第一层拆解：TPOT公式

TPOT 的计算公式如下：

```
TPOT = T_compute + S × T_mem + T_comm × (1 - ρ)
        ↑               ↑              ↑
     计算瓶颈        显存瓶颈        通信瓶颈
```

| 变量 | 含义 | Agent时代变化 | 占TPOT比例 |
|------|------|-------------|-----------|
| **T_compute** | 单Token计算耗时 | 算子融合已优化到接近物理极限 | **已解决** |
| **S** | 有效上下文长度 | 4K→128K，增长32倍 | **主要瓶颈** |
| **T_mem** | KV访存单位耗时 | 显存带宽增长<2倍/年，远跟不上S的增长 | **主要瓶颈** |
| **T_comm** | MoE跨卡通信耗时 | MoE全面替代Dense，占40-60% | **新瓶颈** |
| **ρ** | 通信隐藏率 | 高位运行（>0.7），边际收益小 | 已优化 |

**直接推导出的结论**：

```
T_compute 已优化到位 → 课题不在这里
T_comm（通信）是主要瓶颈 → 课题三（MoE通信压缩）必须做
S × T_mem（显存）是主要瓶颈 → 课题一/二（KV压缩）必须做
```

这就是"为什么要做这些技术"的根逻辑：**不是拍脑袋，是公式告诉我们的**。

---

## 三、第二层拆解：S × T_mem 瓶颈的内部结构

S × T_mem 的含义是：KV Cache 的规模（S）乘以每次访问它的耗时（T_mem）。

```
M_KV = 2 × L × H × D × Bit × S
        ↑
     单请求KV显存占用

B = (M_total - M_weights) / M_KV
        ↑
     单卡并发会话数
```

S 增长 32 倍 → M_KV 增长 32 倍 → B（并发度）被显存容量线性压制

**瓶颈的两条出路**：

| 出路 | 变量 | 具体技术 |
|------|------|---------|
| **减少S**（减少KV总量） | S：有效上下文长度 | 课题一（语义蒸馏压缩）、课题四（VLM视觉压缩） |
| **减少Bit**（减少每份KV的显存） | Bit：量化比特数 | 课题二（头敏感度量化） |

```
减少S → 课题一、四（从源头减少KV生成）
减少Bit → 课题二（从存储格式减少每份KV大小）
两者叠加 → 显存占用 ↓ (S↓ × Bit↓)，B（并发） ↑ 成乘积效应
```

---

## 四、第三层拆解：T_comm 瓶颈的内部结构

MoE 的 All-to-All 通信量由三个因素决定：

```
T_comm ∝ 交换次数 × 字节数/次 × 专家参与量
            ↑           ↑            ↑
        路由策略      量化压缩      Expert跳过
```

**三条技术路径对应三个乘数因子**：

| 因子 | 技术 | 课题 |
|------|------|------|
| 交换次数 | 任务感知协作路由（减少跨设备路由次数） | 课题三 |
| 字节数 | Rank-Aware 通信量化（减少每次传输的字节量） | 课题三 |
| 专家参与量 | 低频专家跳过（减少参与通信的专家数量） | 课题三 |

**三个因子是乘积关系，不是相加关系**：
```
T_comm 降低 = 交换次数↓ × 字节数↓ × 专家参与量↓
            = 30%↓      × 50%↓     × 20%↓
            ≈ 1 - (0.7 × 0.5 × 0.8)
            ≈ 72% 的 T_comm 降低潜力
```

这就是课题三"三路径联合"的真正逻辑——不是"三个技术凑在一起"，而是**三个乘积因子必须同时压缩才能显著降低 T_comm**。

## 五、第四层拆解：吞吐目标的数学表达

```
TPS（吞吐） = B / TPOT
            = (M_total - M_weights) / (M_KV × TPOT_wo_comm)
            = (M_total - M_weights) / (2×L×H×D×Bit×S × TPOT_wo_comm)
```

**吞吐提升 2× 的精确分解**：

```
目标：TPS 提升 2×

路径①：减少 Bit（M_KV↓ → B↑）
  → 课题二：INT4+INT2 混合量化
  → 收益：B ↑约 2×（INT4→INT2 容量翻倍）

路径②：减少 S（M_KV↓ → B↑）
  → 课题一：语义压缩（S 从 128K→有效 20K）
  → 收益：B ↑约 5×（S 压缩 5-6 倍）

路径③：减少 TPOT（不含通信部分）
  → 课题五：Prefill A-FFN 联合（TTFT↓20-30%）
  → 课题六：推测解码协同（TPOT↓20-30%）

路径④：减少 T_comm
  → 课题三：MoE 通信压缩（TPOT↓15-25%）

乘积效应：
  吞吐提升 ≈ B提升因子 × TPOT降低因子
           ≈ 5×(S↓)  ×  2×(Bit↓)  ×  1.4×(TPOT不含通信)
           ≈ 14×
           （说明：实际收益需要打折，但多路径叠加的方向是对的）
```

## 六、技术优先级排序的完整逻辑链

根据瓶颈在公式中的位置，确定技术启动顺序：

```
第一优先级（立即启动）：瓶颈最严重、与公式直接挂钩
├── 课题一（S↓）：S×T_mem 的 S 项，显存瓶颈的主要来源
├── 课题二（Bit↓）：S×T_mem 的 Bit 项，与课题一正交可叠加
└── 课题四（S↓，VLM专用）：VLM场景的S项，576 token是特殊问题

第二优先级（课题一/二验证后启动）：依赖第一优先级建立的测试基础
├── 课题三（T_comm↓）：通信瓶颈，但需要先有压缩框架才能对接
└── 课题五（TTFT↓Prefill计算）：与KV压缩独立，可并行

第三优先级（系统集成）：基于上述课题的技术，形成完整推理系统
├── 课题六（推测解码协同）：系统配置优化，不影响模型输出
└── 课题七（异构调度）：生产环境适配，晚期启动
```

## 七、逐课题回答"为什么要做"

### 为什么要做课题一（KV 语义蒸馏压缩）？

```
根问题：S（有效上下文长度）从 4K→128K 增长了 32 倍，显存增长跟不上
在公式中位置：TPOT = T_compute + S×T_mem + T_comm×(1-ρ)
               → S×T_mem 项是主要瓶颈

课题一解决的是：减少 S（从源头减少 KV 生成）
技术逻辑：
  attention score 只区分"重要程度"
  语义等效的 token 应该在压缩时被视为"等价信息"
  用蒸馏信号（soft label）而非 hard threshold 来判断重要性
  → 比剪枝/量化更保真，因为蒸馏学习的是分布而非离散值

为什么是"蒸馏"而不是"剪枝"：
  剪枝是离散的（保留/丢弃），精度损失是离断式的
  蒸馏是连续的（soft label），可以学到 token 之间的语义关系
  → 在 S 压缩 5 倍的情况下，蒸馏比剪枝更能保持语义完整性
```

### 为什么要做课题二（KV 头敏感度量化）？

```
根问题：M_KV = 2×L×H×D×Bit×S，Bit 控制每份 KV 的显存大小
在公式中位置：M_KV 与 B（并发度）成反比

课题二解决的是：减少 Bit（减少每份 KV 的存储大小）
技术逻辑：
  INT4 是工业标配，INT2 是下一个制高点
  但 INT2 的问题是：不同 attention head 对量化噪声敏感性不同
  深层、attention 聚集型 head 对误差更敏感
  量化敏感 head 用 INT4，不敏感 head 用 INT2
  → 在精度损失 <1% 约束下，最优分配

为什么不是直接用 INT2：
  已有工作（KIVI）验证了 2-bit KV 可行
  但那是 per-token 均匀量化，忽略了 head 间差异
  本课题的创新在于：head-wise 的敏感度分析 + 比特分配
  → 更细粒度 = 相同精度损失下，更低的平均比特数
```

### 为什么要做课题三（MoE 通信三路径联合）？

```
根问题：MoE 架构中 All-to-All 通信占 TPOT 的 40-60%
在公式中位置：T_comm 项

课题三解决的是：T_comm × (1-ρ) 中的 T_comm

技术逻辑（三条乘积因子必须同时压缩）：
  T_comm ∝ 交换次数 × 字节数 × 专家参与量

  为什么三条缺一不可：
    只压缩字节数（量化）：
      交换次数不变，通信次数还是 N 次
      → TPOT 改善有限

    只减少交换次数（路由）：
      字节数不变，每次传输还是 FP16
      → TPOT 改善有限

    只减少专家参与量（跳过）：
      单独使用跳过策略，收益有限（低频专家比例不高）

    三条同时做：
      交换↓30% × 字节↓50% × 参与量↓20%
      → T_comm 降低约 72%，对应 TPOT↓约 30%
```

### 为什么要做课题四（VLM 视觉 Token 压缩）？

```
根问题：VLM 处理一张图片产生 576 个视觉 token，是文本的 10-100 倍
在公式中位置：S（有效上下文）的视觉部分

课题四与课题一的区别：
  课题一：解决文本 token 的 S 问题（attention 模式稀疏）
  课题四：解决视觉 token 的 S 问题（空间相邻 patch 重复）

VLM 为什么必须独立研究：
  冗余来源不同：文本是 attention 稀疏，视觉是空间像素重复
  复用模式不同：LLM 没有"同一图片不同问题"模式，VLM 有
  压缩时机不同：视觉 token 在 Decode 阶段不变化，文本 KV 需要动态追踪

576 token vs 文本典型场景（假设 4K text）：
  576 / 4000 = 14.4%
  → 视觉 token 占比 14%+，且通常 Agent 会处理多张图
  → 实际场景中视觉 S 占总 S 的 50-80%，是显存的主要来源
```

### 为什么要做课题五（Prefill A-FFN 联合）？

```
根问题：TTFT（首 Token 时间）占端到端时延的 60-80%
在公式中位置：T_compute 项（Prefill 阶段）

课题五与课题一/二的关系：
  课题一/二：解决 Decode 阶段的 KV 访存问题（TPOT 的一部分）
  课题五：解决 Prefill 阶段的计算效率问题（TTFT）

为什么 A-FFN 要联合：
  现有剪枝方法（LazyLLM）只跳过 Attention 计算
  但 FFN 计算量是 Attention 的 2-3 倍
  且 Attention 重要的 token 和 FFN 激活强的 token 往往不是同一批
  → 单独优化 Attention 是局部最优，联合优化才是全局最优

为什么优先于其他课题：
  TTFT 是用户感知的最大延迟来源（等首 token 最煎熬）
  但 Prefill 优化独立于 KV 压缩，可以并行启动
```

### 为什么要做课题六（推测解码协同）？

```
根问题：推测解码会额外生成 Draft KV，加重 KV 显存负担
在公式中位置：属于 TPOT 优化，但不影响公式本身

课题六与其他课题的关系：
  其他课题都是"减少已有 KV 的开销"
  课题六是"推测解码引入新 KV 时的最优策略"

为什么需要研究：
  推测解码降低 TPOT，但增加 KV 显存占用
  在 KV 显存已经是主要瓶颈的情况下，推测解码可能反而降低系统吞吐
  → 需要研究如何让推测步数与 KV 压力自适应协调

为什么不优先：
  课题六不影响模型输出精度（是纯系统配置优化）
  而且依赖课题一/二建立的 KV 管理框架
  → 放在第二优先级后期
```

### 为什么要做课题七（异构集群调度）？

```
根问题：生产环境 GPU 集群是异构的（A100/H100 混部）
在公式中位置：不影响 TPOT 公式，但影响实际部署的吞吐

课题七与其他课题的关系：
  课题一至六：解决单卡/同构集群内的算法效率问题
  课题七：解决异构集群下的调度效率问题

为什么是最后：
  异构环境是"锦上添花"而非"雪中送炭"
  同构集群下课题一至六能正常工作
  异构集群只是让同样的技术发挥受限
  → 课题七的收益是建立在课题一至六之上的
```

# 第一章：洞察——三个被忽视的关键发现

## 1.1 发现一：B 与 TPOT 的对偶关系是最重要的约束

**问题**：大多数 KV 压缩技术规划只关注"压缩能带来什么收益"，但没有计算"压缩本身要付出什么代价"。

```
压缩的直接收益：
  M_KV↓ → B↑ → TPS↑

压缩的间接代价：
  压缩/解压操作引入额外计算
  → TPOT↑
  → 部分抵消 B↑ 的收益
```

**对偶关系的数学表达**：

```
TPS = C / TPOT
    = C / (T_calc + S × T_mem + T_comm)

M_KV 压缩后：
  M_KV_new = M_KV × α（α < 1，压缩比）
  B_new = B / α

  但 TPOT 可能增加：
  TPOT_new = TPOT × β（β > 1，压缩开销因子）

  净吞吐变化：
  TPS_new / TPS = (B/α) / (TPOT × β) = (B/TPOT) / (α × β)
```

**关键洞察**：只有当 α × β < 1 时，压缩才是合算的。

```
→ Bit 量化（α=0.5，β≈1.0）：几乎免费
  量化在显存层做，解压后参与计算的方式不变
  → 最干净的 B↑ 手段

→ S 剪枝（α=0.125，β>1.0）：需要验证
  剪枝后的 token 访问需要重计算
  → 必须验证 β 是否足够小

→ 跨请求缓存（α≈0，β<1）：最优
  命中时直接跳过计算，不增加 TPOT
  → 唯一带来免费午餐的方向
```

## 1.2 发现二：三个目标不是独立的，而是乘积关系

**目标体系**：

```
① 推理时延：1.5× 加速
  → TTFT↓33% + TPOT↓33%

② 系统吞吐：2× 提升
  → TPS = C / TPOT

③ 模型精度：损失 ≤ 1%
  → 约束所有优化方向的上限
```

**三个目标的乘积关系**：

```
2× 吞吐提升不能靠单一优化实现，必须多路径叠加：

Bit↓（课题B）        → B↑ 2×
T_comm↓（课题D）      → TPOT↓ 1.33×
跨请求缓存（课题G）   → 命中时 B↑ 1.3× + TTFT↓ 35%

叠加效果：2× × 1.33× × 1.3× ≈ 3.5× > 2× ✅

关键：不同维度的优化乘积叠加，而非单一维度的线性累加
```

## 1.3 发现三：S 压缩在 TTFT 和 TPOT 中含义不同

**被忽视的细节**：S 在 TTFT 和 TPOT 中代表不同的物理量。

```
TTFT 中的 S：S_input（输入序列长度）
  → 用于计算 Prefill 计算量
  → S_input × T_calc_ffn

TPOT 中的 S：S_kv（当前 KV 缓存长度）
  → S_kv = S_input + 已生成 token 数
  → 在生成过程中不断增长
  → S_kv(t) = S_input + t - 1
```

**实际影响**：

```
这意味着 TPOT 不是恒定值，而是随生成过程增长：

Decode 第 1 步：S_kv = S_input
Decode 第 10 步：S_kv = S_input + 9
Decode 第 100 步：S_kv = S_input + 99

TPOT(1) < TPOT(10) < TPOT(100)

→ TPS = C / TPOT 也是近似值（用均值或 P99 代表）
→ 规划中使用均值是合理的
```

## 课题一：Head-wise 敏感度自适应的 KV 混合精度量化

### 目标来源

```
目标：系统吞吐 2×
变量链：Bit↓ → M_KV↓ → B↑ → TPS↑
维度：唯一直接影响 B 的量化方向（Bit 是 M_KV 的独立因子）
```

### 关键洞察

```
M_KV = 2 × L × H × D × (Bit/8) × S

Bit 量化的独特价值：
  Bit 只影响 M_KV（→ B↑）
  不影响 TPOT_wo_M_KV（量化在显存层，解压后计算方式不变）

这是与 S 剪枝的本质区别：
  S 剪枝：减少计算量 → 可能增加 TPOT↑（重计算开销）
  Bit 量化：减少存储量 → 对 TPOT 计算几乎无影响

因此：Bit 量化是最"干净"的 B↑ 手段
```

### 技术方案

```
① Head-wise 敏感度分析（离线，一次性）
   梯度敏感度：loss 对各 head KV 量化误差的梯度
   Attention 方差：高方差=聚集型=h敏感，低方差=分散型=l敏感
   联合评分 → head 敏感度排序表

② RoPE 频域感知量化（在线）
   低频分量（前 d/2 维度）→ INT4
   高频分量（后 d/2 维度）→ INT2

③ 多轮感知精度补偿
   前序轮次 → INT4（精度优先）
   当前轮次 → INT2（容量优先）
```

### 假设验证

| 假设 | 验证方法 | 通过标准 |
|------|---------|---------|
| H1：Head-wise 敏感度差异显著 | 梯度敏感度+attention方差分析 | top/bottom head 差异 > 5% |
| H2：INT2 perplexity 损失 < 1% | LongBench 上测 INT2 perplexity | < 1% |
| H3：RoPE 频域分块有效 | 对比低频 INT4 vs 全 INT4 | 差异 > 0.3 perplexity |

### 技术指标

```
M_KV↓：Bit 从 16→4（INT4），局部 INT2 面积 30%
B↑：2×（理论），验证 > 1.5×
精度：LongBench perplexity 损失 < 1%
```

## 课题二：蒸馏信号感知的 KV 动态剪枝与 B↑-TPOT↑ 对偶关系验证

### 目标来源

```
目标：系统吞吐 2×
变量链：S↓ → M_KV↓ → B↑ → TPS↑
维度：与 Bit 量化并列，共同压缩 M_KV
关键：必须验证 TPOT↑ 开销能否被 B↑ 收益覆盖
```

### 关键洞察

```
现有 KV 剪枝方法的问题：
  H2O：按 attention score 排序（单一维度）
  SnapKV：按语义聚类（结构维度）
  LazyLLM：按需恢复（动态维度）

三者共同局限：
  → 依赖离散的 importance score
  → 无法捕捉 token 之间的语义关联强度

蒸馏的核心价值（Hinton 2015）：
  → Soft label 包含类别之间的相对距离
  → 比 hard label 更丰富

迁移到 KV 压缩：
  Teacher = 完整 KV 的 attention 分布
  Student = 压缩后 KV 的 attention 分布
  Loss = KL(Student || Teacher)

→ 每个 token 的"蒸馏重要性分数"比 attention score 多包含"语义关联"信息
```

### 技术方案

```
① 蒸馏信号提取（Prefill，一次性）
   Teacher = 完整 KV attention 分布
   计算每个 token 的 KL 贡献度
   → 蒸馏重要性分数

② 语义等效 token 识别
   相邻 token embedding cosine 相似度 > 0.9
   → 识别为可合并的语义等效组
   → 组内仅保留 attention score 最高的 token 的 KV

③ B↑-TPOT↑ 对偶关系验证（核心）
   每 N 步评估：
     B 提升比例 = 1 / 压缩比
     TPOT 开销比例 = 测量值
   净收益 = B↑ / TPOT↑

   决策：
     净收益 > 2 → 继续压缩
     净收益 < 1 → 触发失效保险
```

### 假设验证

| 假设 | 验证方法 | 通过标准 |
|------|---------|---------|
| H1：蒸馏信号与 attention score 互补 | Pearson 相关系数 | < 0.7 |
| H2：在线蒸馏开销 < Prefill 5% | 实测额外延迟 | < 5% |
| H3：B↑ 收益 > TPOT↑ 开销 | 计算净收益 | > 2 |

### 技术指标

```
S↓：128K → 16K（8× 压缩，验证 3× 保底）
B↑：验证 > 1.5×
TPOT↑：< 20%（失效保险：> 50% 则终止）
精度：LongBench 损失 < 1%
净收益：> 2×
```

### 失效保险

```
触发条件：H3 验证失败（净收益 < 1）
动作：终止 S 剪枝方向
备选：以课题一（Bit 量化）为主要 B↑ 手段

触发条件：H1 验证失败（相关性 > 0.9）
动作：蒸馏信号无额外价值
备选：退回到 SnapKV 语义聚类方案
```

## 课题三：Rank-Aware MoE 通信量化

### 目标来源

```
目标：推理时延 1.5× + 系统吞吐 2×
变量链：T_comm↓ → TPOT↓ → TPS↑ + 时延↓
维度：唯一直接影响 TPOT 且不影响 B 的方向（无对偶冲突）
```

### 关键洞察

```
T_comm 优化的独特价值：
  ① 直接降低 TPOT → TPS↑（直接）
  ② 不影响 M_KV → B 不变（无副作用）
  ③ 与 Bit/S 压缩正交，可叠加

三个独立因子：
  T_comm = 交换次数 × 字节数/次 × Expert 参与量

核心问题（未被显式解决）：
  量化噪声导致 top-k Expert 排名翻转
  → Expert_7（量化前 top-1）变成 Expert_3（量化后 top-1）
  → 路由错误 → 模型输出质量下降

Rank-Aware Jaccard Loss：
  L = L_routing + λ × L_jaccard
  L_jaccard = max(0, 0.9 - Jaccard(top-k_pre, top-k_post))
```

### 技术方案

```
① Top-k 排名稳定性分析（离线）
   在测试集上统计：
     量化前 top-k Expert 集合
     量化后 top-k Expert 集合
     Jaccard 相似度

② Rank-Aware 量化（训练/微调时引入）
   Top-k Expert → FP8（高保真）
   组内非 top-k → INT4
   组外 → 跳过

③ 三步流水线（工程集成）
   Step 1：低频 Expert 跳过（减少参与量）
   Step 2：协作约束路由（减少交换次数）
   Step 3：Rank-Aware 量化（减少字节数）
```

### 假设验证

| 假设 | 验证方法 | 通过标准 |
|------|---------|---------|
| H1：Jaccard(top-k) < 0.9 | 实测量化前后 top-k 相似度 | < 0.9 |
| H2：Rank-Aware perplexity 损失 < 0.5% | 对比有无约束的 perplexity | < 0.5% |
| H3：三步流水线 TPOT↑ < 10% | 实测总延迟 | < 10% |

### 技术指标

```
T_comm↓：30-50%（三步叠加）
TPOT↓：15-25%
B：不变（无副作用）
精度：perplexity 损失 < 1%
```

## 课题四：空间语义双维度协同的视觉 KV 压缩

### 目标来源

```
目标：系统吞吐 2×
变量链：S_visual↓ → M_KV↓ → B↑ → TPS↑
维度：VLM 场景专用，S_visual 是总 S 的 50-80%
```

### 关键洞察

```
VLM 视觉 token 的冗余来源与文本完全不同：

文本 KV 冗余：attention 模式稀疏
  → 压缩依据：attention score

视觉 token 冗余：空间相邻 patch 重复
  → 压缩依据：像素级相似度

典型数据：
  一张 224×224 图片 → 576 个 visual token
  4 张图 → 2304 个 visual token
  总 S = 1K 文本 + 2.3K 视觉 = 3.3K
  视觉占 S 的 70%

这是 LLM 不存在的独特问题，必须独立研究。
```

### 技术方案

```
① 空间聚类（Prefill，一次性）
   ViT 编码后 576 token
   CLIP embedding → K-means 空间聚类
   相邻 patch 被自动合并到同一语义簇

② Attention 筛选（Prefill）
   各簇与 query 的 cross-attention
   高关联 → 保留完整 KV
   低关联 → INT4 压缩

③ 空间-语义双维度协同
   空间维度：相邻 patch 像素相似度
   语义维度：簇与 query 的 cross-attention
   两者正交 → 高空间冗余 × 高语义相关 = 优先压缩计算
```

### 假设验证

| 假设 | 验证方法 | 通过标准 |
|------|---------|---------|
| H1：相邻 patch CLIP 相似度 > 0.9 | 计算均值 | > 0.9 |
| H2：空间聚类 + attention 互补性强 | Jaccard overlap | < 0.85 |
| H3：VLM 场景 B↑ 净收益 > 1.5 | 计算 B↑/TPOT↑ | > 1.5 |

### 技术指标

```
视觉 token 压缩：50%+
S_visual↓：576 → 288
VLM 场景吞吐：提升 > 1.5×
精度：多模态 benchmark 损失 < 2%
```

## 课题五：视觉语义指纹缓存

### 目标来源

```
目标：推理时延 1.5× + 系统吞吐 2×
变量链：缓存命中 → TTFT↓ + B_equiv↑
维度：唯一不引入 TPOT↑ 的优化方向（免费午餐）
```

### 关键洞察

```
vLLM RadixAttention 的局限：
  → 只能识别精确的文本前缀匹配
  → 无法识别"同一图片+不同问题"

新缓存维度：
  图片语义指纹 = CLIP embedding → LSH hash
  作为独立于文本前缀的缓存键

命中时：
  → 跳过图像 ViT 编码（TTFT↓）
  → 跳过图像 self-attention KV 计算（节省计算 = 等效 B↑）
  → 只重新计算 cross-attention（query 不同，结果不同）

命中条件：
  文本前缀相同 + 图像指纹相同
```

### 技术方案

```
① 视觉语义指纹编码
   CLIP 图像编码器 → 全图 embedding
   局部敏感哈希（LSH）→ 128-bit 指纹
   碰撞率 < 1%

② 双维度缓存索引
   缓存键 = 文本前缀 hash + 图像指纹 hash
   两套独立维护

③ 跨模态复用策略
   命中：图像 self-attention KV 复用，只算 cross-attention
   未命中：正常计算完整图像 KV
```

### 假设验证

| 假设 | 验证方法 | 通过标准 |
|------|---------|---------|
| H1：指纹碰撞率 < 1% | 在图片集上测碰撞率 | < 1% |
| H2：同图不同问比例 > 30% | 统计数据集 | > 30% |
| H3：命中时 TTFT↓ 可覆盖未命中 TPOT↑ | 计算期望值 | > 0 |

### 技术指标

```
缓存命中率：> 60%
TTFT↓：命中时 35%+
吞吐提升：> 1.3×
```

## 课题六：Attention-FFN 联合重要性评估与选择性计算

### 目标来源

```
目标：推理时延 1.5×
变量链：FFN 跳过 → TTFT↓ → 时延↓
维度：唯一直接影响 TTFT 的独立方向（与其他课题正交）
```

### 关键洞察

```
FTP（ICLR 2025）的贡献：
  → 验证了 FFN 激活存在动态稀疏
  → 跳过 FFN 输出接近零的 token

FTP 的局限：
  → 只跳过 FFN，不跳过 KV
  → 单独优化 FFN 和单独优化 attention 都是局部最优

联合重要性评估的发现：
  Attention 重要的 token 和 FFN 激活强的 token 往往不是同一批

  高 attn + 高 FFN → 全量计算
  高 attn + 低 FFN → 跳过 FFN（保留 attn）
  低 attn + 高 FFN → 保留 FFN（跳过 attn，罕见）
  低 attn + 低 FFN → 跳过两者
```

### 技术方案

```
① FFN 激活模式分析（Prefill）
   实测 FFN 输出激活值分布
   识别激活值接近零的 token

② Attention-FFN 联合评估
   对每个 token 计算：
     attention_score
     ffn_activation
   建立 2×2 象限矩阵

③ 源头 KV 联动（可选扩展）
   FFN 不重要 → KV 大概率也不重要
   → 源头减少 KV 生成
   → 需要独立验证 B 和 TPOT 变化
```

### 假设验证

| 假设 | 验证方法 | 通过标准 |
|------|---------|---------|
| H1：attention 和 FFN 重要性 Jaccard < 0.8 | 计算 overlap | < 0.8 |
| H2：A-FFN 联合比单独 FFN 跳过 TTFT↓ 更多 | 对比 | > 10% |
| H3：源头 KV 联动不引入 TPOT↑ | 测 B 和 TPOT | TPOT↑ < 5% |

### 技术指标

```
TTFT↓：20-30%
Prefill 计算量↓：35-40%
精度：≤ 1%
```

## Step 0：目标体系分析（被忽视的核心维度）

### 0.1 三个目标不是独立的，而是相互制约的

```
目标体系：
  ① 推理时延：1.5×加速（TTFT + TPOT 均降低33%）
  ② 系统吞吐：2×提升（TPS = B / TPOT）
  ③ 模型精度：损失 ≤ 1%

三个目标的关系：
  ②的系统吞吐公式 → TPS = B / TPOT
  B = (M_total - M_weights) / M_KV
  M_KV = 2 × L × H × D × Bit × S

  → TPOT 和 B 通过 M_KV 耦合！
  → 不是"分别优化三个目标"，而是"在 M_KV 的约束下联合优化"
```

### 0.2 吞吐 2× 的数学拆解

```
目标：TPS 提升 2×

TPS = B / TPOT = (M_total - M_weights) / (M_KV × TPOT_wo_M_KV)

M_KV = 2 × L × H × D × Bit × S

代入：
TPS = (M_total - M_weights) / (2 × L × H × D × Bit × S × TPOT_wo_M_KV)

因此 TPS 提升 2× 等价于：
  (Bit × S × TPOT_wo_M_KV) 整体降低 2×

三个独立乘积因子：
  ① Bit（量化精度）→ 影响 M_KV
  ② S（有效上下文长度）→ 影响 M_KV
  ③ TPOT_wo_M_KV（不含 M_KV 的 TPOT）→ 影响 TPOT

2× 吞吐的精确分解（不是任意的，是可加的）：
  Bit↓ → M_KV↓ → B↑ → TPS↑
  S↓   → M_KV↓ → B↑ → TPS↑
  TPOT_wo_M_KV↓ → TPOT↓ → TPS↑

三个乘积因子必须同时优化，才能达到 2×！
```

### 0.3 B 与 TPOT 的对偶关系（这是之前最大的遗漏）

```
关键发现：M_KV 压缩同时影响 B 和 TPOT，但方向相反！

M_KV 压缩的直接影响：
  → M_KV↓ → B↑（并发度↑，吞吐↑）
  → 这是正面效果

M_KV 压缩的间接影响（之前被忽略）：
  → 压缩/解压操作本身有计算开销
  → 压缩后的数据访问可能更复杂（需要解压+重计算）
  → 可能导致 TPOT↑（吞吐↓）
  → 这是负面效果

对偶关系：
  ┌─────────────────────────────────────────────┐
  │  M_KV 压缩    ──── + ────→    B↑           │
  │     ↓                                     │
  │     ↓（压缩计算开销）                      │
  │     ↓                                     │
  │  ──── - ────→  TPOT↑（部分抵消B↑收益）   │
  └─────────────────────────────────────────────┘

结论：不是"压缩 M_KV 就一定能提升吞吐"
      关键是：压缩带来的 B↑ 收益 > 压缩本身带来的 TPOT↑ 开销
      → 净收益 = f(B↑) - g(TPOT↑) > 0 才值得做
```

### 0.4 TTFT 的独立性与重要性

```
TTFT = T_prefill + T_sched

TTFT 与 TPS 的关系：
  TTFT 影响的是"第一个 token 的响应速度"
  TPS 影响的是"稳定状态的吞吐量"

但 TTFT 与吞吐不是独立的：
  TTFT↓ → T_sched↓ → 整体时延↓ → TPS间接改善

TTFT 优化的特点：
  TTFT 主要在 Prefill 阶段
  Prefill 计算量 = Attention 计算 + FFN 计算
  FFN 计算量是 Attention 的 2-3 倍
  → FFN 优化是 TTFT 优化的关键

TTFT 优化与其他目标的关系：
  TTFT 优化（课题E）不影响 M_KV
  → 与 B 和 TPOT 无对偶关系
  → 是独立的优化方向
  → 可以与其他课题并行推进
```

### 0.5 三个目标的完整优化地图

```
                    ┌─────────────────────────────────────┐
                    │         三个目标 × 优化维度          │
                    └─────────────────────────────────────┘

维度1：M_KV 压缩（影响 B 和 TPOT）
  Bit↓（量化）→ B↑（好），但可能 TPOT↑（坏）
  S↓（剪枝）→ B↑（好），但可能 TPOT↑（坏）
  → 需要验证：压缩的 B↑ 收益 > TPOT↑ 开销

维度2：TPOT_wo_M_KV 优化（只影响 TPOT，不影响 B）
  T_comm↓（MoE 通信）→ TPOT↓
  → 与 M_KV 压缩正交，可叠加

维度3：TTFT 优化（只影响 TTFT，不影响 B 和 TPOT_wo_M_KV）
  A-FFN 联合优化 → Prefill 计算量↓
  → 与维度1、2 正交，可叠加

维度4：跨请求复用（影响 TTFT 和 B，不影响 TPOT）
  缓存命中 → 跳过 Prefill 计算 → TTFT↓
  缓存命中 → 减少重复计算 → 等效于 B↑

三个目标 × 四个维度的覆盖矩阵：

维度              │ 影响目标     │ 与M_KV压缩的冲突？
─────────────────┼────────────┼──────────────────
① Bit 量化       │ B↑ TPOT↓  │ 可能冲突（解压开销）
② S 剪枝         │ B↑ TPOT↓  │ 可能冲突（重计算开销）
③ T_comm 通信    │ TPOT↓      │ 无冲突
④ A-FFN Prefill  │ TTFT↓      │ 无冲突
⑤ 跨请求缓存     │ TTFT↓ B↑   │ 无冲突
```

### 0.6 修正后的 TPOT 因果图

```
TPOT = T_compute + S × T_mem + T_comm × (1 - ρ)
         ↑              ↑              ↑
     TTFT 的主要      M_KV 的来源     TPOT_wo_M_KV 的
```

## Step 3：修正后的课题体系

### 课题A（修正）：B↑ 与 TPOT↑ 对偶关系验证驱动的文本KV剪枝

**来源**：目标2的 B↑ 需求 × 对偶关系约束

**关键修正**：之前只关注"剪枝能减少 S"，现在必须回答：

```
压缩前：B = M_KV_baseline
压缩后：B = M_KV_new = M_KV_baseline × 压缩比

压缩的收益：B 提升比例 = 1 / 压缩比
  例如：S 从 128K→16K，压缩比=8，B 提升 8 倍

压缩的开销：TPOT 增加比例 = f(压缩算法开销)
  例如：每步重计算开销 +5%，则 TPOT↑5%

净收益：B 提升 ÷ TPOT↑ = 8 ÷ 1.05 ≈ 7.6×（好）
       但如果 TPOT↑20%，则净收益 = 8 ÷ 1.2 ≈ 6.7×（还是好）
       如果 TPOT↑100%，则净收益 = 8 ÷ 2.0 = 4×（差）

关键阈值：TPOT↑ < 100% 才有净收益
          实际目标：TPOT↑ < 50%，B↑ > 4×
          → 净收益 > 2×
```

**核心问题**：剪枝带来的 TPOT↑ 开销到底有多大？这个开销能否被 B↑ 收益覆盖？

**假设清单**：

| 假设 | 验证状态 | 验证方法 |
|------|---------|---------|
| **假设A**：剪枝后重计算开销 TPOT↑ < 50% | □未验证 | 实测剪枝方案在 decode 阶段的额外计算延迟 |
| **假设B**：B↑的收益能覆盖 TPOT↑ 的开销 | □未验证 | 计算：B提升比例 / TPOT↑ 比例 > 2 |
| **假设C**：剪枝的精度损失 < 1% | □未验证 | 在 LongBench 上测 benchmark |

**结论**：这个课题的核心价值不是"证明剪枝能减少 S"，而是**"验证 B↑ 能否覆盖 TPOT↑ 的对偶关系"**。

### 课题B（修正）：M_KV 压缩优先的 Head-wise 混合精度量化

**来源**：目标2的 B↑ 需求，Bit 是 M_KV 的独立因子

**关键洞察**：

```
M_KV = 2 × L × H × D × Bit × S

Bit 的特殊价值：
  Bit 只影响 M_KV（→ B），不影响 TPOT_wo_M_KV
  （量化在显存层面做，解压后参与计算的方式不变）

这是与 S 剪枝的本质区别：
  S 剪枝：减少计算量（可能增加 TPOT 开销）
  Bit 量化：减少存储量（B↑），对 TPOT 计算部分无直接影响
           （除非解压成为瓶颈）

因此：Bit 量化是最"干净"的 B↑ 手段
     优先于 S 剪枝
```

**技术目标**：M_KV↓ → B↑ 2×，TPOT 计算部分不变，精度损失 < 1%

**关键技术**：

```
① Head-wise INT4/INT2 混合量化（对 TPOT 无额外开销）
   INT4 是工业标准，vLLM 已优化解压速度
   INT2 需要验证：是否带来解压瓶颈？
   Head-wise 分配：敏感 head→INT4，不敏感 head→INT2

② 解压延迟验证
   核心问题：INT2 的解压是否比 INT4 解压慢到影响 TPOT？
   → 如果解压不成为瓶颈：Bit↓ = 纯粹的 B↑ 收益
   → 如果解压成为瓶颈：需要量化感知调度

③ 多轮感知精度补偿
   前序轮次 INT4，当前轮次 INT2
   精度损失 < 1%
```

**假设清单**：

| 假设 | 验证状态 | 验证方法 |
|------|---------|---------|
| **假设A**：INT2 解压不成为 TPOT 瓶颈 | □未验证 | 实测 INT2 vs INT4 的 decode 单步延迟差异 |
| **假设B**：Head-wise 分配下精度损失 < 1% | □未验证 | 在 LongBench 上测 INT2 perplexity |
| **假设C**：RoPE 频域感知进一步提升精度 | □部分验证 | Block-GTQ 已验证块级，频域分块未验证 |

### 课题D（修正）：MoE 通信压缩（唯一同时改善 TPOT 且不影响 B 的方向）

**来源**：目标1（TPOT↓）+ 目标2（TPS 中 TPOT↓）

**关键洞察**：

```
T_comm 优化的独特价值：
  ① 直接降低 TPOT → TPS↑（直接）
  ② 不影响 M_KV → B 不变（无副作用）
  ③ 与 Bit/S 压缩正交，可叠加

三个独立因子：
  T_comm = 交换次数 × 字节数/次 × Expert 参与量
           ↓           ↓           ↓
          课题D2      课题D1       课题D3
        （协作路由）（字节量化）（Expert跳过）

三者联合的净收益：
  T_comm↓ → TPOT↓ → TPS↑
  B 不变（无对偶关系冲突）
  → 这是最干净的 TPS 提升手段
```

**技术目标**：T_comm↓33%，TPOT↓20-25%，B 不变，TPS↑ 直接受益

**关键技术**（三步流水线）：

```
① Expert 跳过（课题 D3）：减少参与量
   低频 Expert 直接跳过，不触发通信

② 协作约束路由（课题 D2）：减少交换次数
   高频共激活 Expert 同置，减少跨设备路由

③ Rank-Aware 量化（课题 D1）：减少字节数
   Top-k Expert 用 FP8，组内非 top-k 用 INT4
   显式约束 Jaccard(top-k_pre, top-k_post) ≥ 0.9
```

**假设清单**：

| 假设 | 验证状态 | 验证方法 |
|------|---------|---------|
| **假设A**：Rank-Aware 量化不会因约束过多导致 perplexity 损失 | □未验证 | 对比有无 Rank-Aware 约束的 perplexity |
| **假设B**：三步流水线的总开销 < 单步的 1.5 倍 | □未验证 | 估算三步各自的延迟，测总开销 |
| **假设C**：T_comm↓ 能带来 TPOT↓ 的显著收益 | □已验证 | DeepSeek 官方数据：通信占 TPOT 47.1% |

```
   识别 FFN 激活值接近零的 token

② Attention-FFN 联合重要性评估
   高 attn + 高 FFN → 全量计算
```

```
                       ↑              ↑
```

**关键判断**：
- T_compute 已接近物理极限（FlashAttention/Tensor并行已系统性解决）→ **不作为主攻**
- S×T_mem 是**主要瓶颈**（Agent多轮使S增长32倍，显存增长<2倍）
- T_comm 是**新瓶颈**（MoE全面替代Dense，通信占40-60%）

## Step 1：业务约束六问

| 问题 | 答案 | 结论 |
|------|------|------|
| Q1: 单卡还是多卡？ | **多卡**（MoE架构：DeepSeek-V3/Kimi K2/Qwen3-Max） | 通信压缩是必选项 |
| Q2: 序列长度分布？ | **128K~1M**（Agent多轮plan→act→observe→reflect） | KV Cache是主要显存消费者 |
| Q3: 延迟要求？ | **TPOT领先30%** | 必须解决KV访存瓶颈 |
| Q4: 最大并发？ | **数十至数百路**（Agent多路并发） | 显存容量是硬约束 |
| Q5: 精度容忍度？ | **≤1%** | INT4是上线，INT2需验证 |
| Q6: 模型类型？ | **MoE架构** | 通信是新瓶颈，与KV瓶颈必须同时解决 |

**六问结论**：
```
KV Cache压缩 + MoE通信压缩 = 两个必选项，缺一不可
精度约束：INT4是上线，INT2需验证后才可用
```

## Step 4：从空白格推导课题命题

### 课题一：蒸馏信号感知的KV语义选择性压缩技术

**来源格子**：③ KV×蒸馏（空白格，前瞻★★★★★+回溯★★★★★）

**关键挑战**：S×T_mem是TPOT主要瓶颈，现有KV压缩（H2O/SnapKV/LazyLLM）依赖attention score或语义聚类，但attention score只区分重要程度，**无法识别语义等效但score不同的token对**。蒸馏的soft label（Hinton 2015）包含token间的语义关联度信息，比单一score更丰富，但从未被应用于KV压缩领域。

**技术目标**：128K长上下文场景，KV显存↓3-5倍，吞吐↑30-50%，精度损失<1%

**关键技术**：
```
① 蒸馏信号提取（Prefill阶段，一次性）
   机制：提取完整KV的attention分布作为teacher soft label
   对应假设：假设A（待验证）

② 语义等效token识别
   机制：embedding space cosine相似度，识别"语义等效但score不同"的token对
   对应假设：假设C（待验证）

③ 蒸馏感知的重要性预算分配（Decode阶段）
   机制：L_distill + λ×cost联合优化，每N步重新优化budget
   对应假设：假设B（待验证）

失效保险：见Step 4.5
```

### 课题二：头敏感度自适应的KV混合精度量化技术

**来源格子**：① KV×量化（活跃格，前瞻★★★★★+回溯★★★★）

**关键挑战**：M_KV = 2×L×H×D×Bit×S，Bit项决定并发上限。INT4已是工业标配，INT2是下一个制高点——在相同显存下INT2比INT4容量多一倍。但per-token均匀INT2量化会导致严重perplexity下降。KVTuner已验证layer-wise敏感性，Block-GTQ已验证RoPE频域感知，但**head-wise + 频域联合**仍无人做。

**技术目标**：LLM推理，TTFT↓15-20%，TPOT↓20%，并发能力↑1.5-2×，精度损失<1%

**关键技术**：
```
① Head-wise敏感度分析（离线标定）
   机制：梯度敏感性+attention方差联合，建立head敏感度排序表
   对应假设：假设A（待验证）

② RoPE频域感知量化（在线执行）
   机制：低频块→INT4，高频块→INT2
   对应假设：假设C（部分验证，Block-GTQ已验证块级）

③ 多轮感知精度补偿
   机制：前序轮次INT4，当前轮次INT2+补偿模块
   对应假设：假设B（待验证）

失效保险：见Step 4.5
```

### 课题三：MoE通信三因子流水线式联合压缩技术

**来源格子**：⑩⑪⑫三格联动（空白/少但活跃，前瞻★★★★★+回溯★★★★）

**关键挑战**：T_comm占TPOT 40-60%，但T_comm = 交换次数 × 字节数 × 专家参与量，**三个因子必须同时压缩才能显著降低T_comm**。现有工作只做单一路径（量化或路由或跳过），三路径从未被系统联合。

**技术目标**：多卡MoE推理，交换↓30%，字节↓50%，TPOT↓15-25%，精度损失<1%

**关键技术**（流水线式，非同时优化）：
```
Step 1（预处理）：低频Expert跳过
   机制：历史激活统计→低频名单→路由前排除
   对应假设：假设A（待验证）

Step 2（路由）：任务感知协作约束
   机制：任务类型→协作分组→高频专家同置
   对应假设：假设C（待验证）

Step 3（通信）：Rank-Aware量化
   机制：top-k专家→FP8，组内非top-k→INT4
   对应假设：假设B（待验证）

失效保险：见Step 4.5
```

### 课题四：FFN跳过与KV生成联动的Prefill选择性计算技术

**来源格子**：⑧ A×稀疏 + ③ KV×蒸馏联动（新方向，前瞻★★★★+回溯★★★）

**关键挑战**：TTFT占端到端时延60-80%，FFN计算量是Attention的2-3倍。FTP已验证FFN稀疏跳过的可行性，但FTP只跳过FFN不跳过KV。**核心洞察：FFN激活不重要的token，其KV大概率也不重要**——两者联动可以从源头减少KV生成。

**技术目标**：长序列（>32K）Prefill，TTFT↓20-30%，计算量↓35-40%，精度损失≤1%

**关键技术**：
```
① FFN激活稀疏感知（Prefill阶段）
   机制：分析FFN激活模式，识别接近零的token
   对应假设：假设A（待验证）

② Attention-FFN联合重要性评估
   机制：attention score方差+FFN激活稀疏度联合判断
   对应假设：假设B（待验证）

③ 源头KV联动
   机制：FFN不重要→KV也不生成，从源头节省
   对应假设：假设A/B

失效保险：见Step 4.5
```
