# 推理压缩技术全景图 - 方法论 v2.0

> 版本: v2.0 | 日期: 2026-06-28
> 适用: AI推理压缩领域的技术全景梳理
> **v2.0 新增：反方证据 + 跨格子协同 + 子技术涌现规则**

---

## 一、核心思想

**根技术不是定义出来的，是从论文聚类中归纳出来的。**

传统工作流：先定义根技术 → 再分类论文（先入为主，遗漏未知）

本方法论：先聚类论文 → 再归纳根技术 → 自然涌现（数据驱动，全面）

---

## 二、三阶段工作流

```
论文采集与分类 → 论文精读 → 技术提炼与全景图
   （涌现根技术）  （深入验证）  （结构化输出）
```

### 阶段一：论文采集与分类

**目标**：建立带分类的论文集合

| 步骤 | 内容 | 工具/方法 |
|------|------|-----------|
| 1 | 从corpus提取论文 | inference_compression_strict.json (2757篇) |
| 2 | 关键词检索补充 | arXiv API / 会议论文集 |
| 3 | 去重与质量筛选 | 标题/作者哈希去重 |
| 4 | 机器批量摘要 | LLM摘要：方法/贡献/挑战 |
| 5 | 向量化聚类 | embedding + KMeans/HDBSCAN |
| 6 | 人工审阅聚类 | 修正聚类边界、合并相似簇 |
| 7 | 按技术分类打标签 | KVCache/通信/显存/计算/... |

**交付物**：
- 分类后的论文清单 `papers_classified.json`
- 每篇摘要 `papers_summaries.json`
- 聚类结果 `paper_clusters.json`

**关键原则**：
- 聚类在前，标签在后
- 人工审阅必须有，避免纯机器误分类
- 保留"未分类"标签，留给后续发现的新方向

## 三、v2.0 新增：跨格子协同分析

> **v1 缺失**的跨格子分析，导致课题可能冲突或重复

### 3.1 跨格子协同矩阵

**协同关系（绿色 = 正向）**：

| 组合 | 协同度 | 说明 |
|------|-------|------|
| K×Q + K×S | **高** | KV 量化 + KV 稀疏可联合优化（先稀疏后量化） |
| M×Q + M×D | **高** | 模态编码器量化 + 蒸馏协同（先量化后蒸馏） |
| C×Q + C×S | **中** | 通信量化 + 通信稀疏 |
| K×Q + K×L | **中** | KV 量化 + KV 低秩（MLA 路线） |
| K×S + C×G | **中** | KV 协同共享 + 通信优化 |

**冲突关系（红色 = 负向）**：

| 组合 | 冲突度 | 说明 |
|------|-------|------|
| K×Q + K×S（极端） | **高** | INT2 量化 + 90% 稀疏 → 精度崩溃 |
| M×Q + M×S（极端） | **高** | INT2 量化 + 95% 稀疏 → 精度崩溃 |
| A×Q + A×S | **中** | 激活量化 + 激活稀疏可能冲突 |
| W×P + W×L | **中** | 剪枝 + 低秩可能双重压缩导致过拟合 |

### 3.2 跨格子分析模板

```markdown
## 课题 X：跨格子分析

### 涉及格子
- 主要格子：[对象×方法]
- 协同格子：[可能协同的格子]
- 冲突格子：[可能冲突的格子]

### 协同机会
- 协同格子 1：说明
- 协同格子 2：说明

### 冲突风险
- 冲突格子 1：说明
- 缓解方案：

### 跨场景复用
- 在 [场景 X] 适用
- 在 [场景 Y] 部分适用
- 在 [场景 Z] 不适用
```

### 3.3 跨格子课题的优先级调整

```
如果课题涉及多个格子（协同）：
  → 优先级 +1（例如 P1 → P0 边界）
  
如果课题涉及冲突格子：
  → 优先级 -1（需要风险缓解）
  
如果课题在多场景通用：
  → 综合得分 +20%
```

## 四、子技术涌现规则（v2.0 增强）

> **v1 缺失**的子技术选型规则

### 4.1 涌现过程

```
论文聚类结果
  ↓
每个 (对象×方法) 格子内有若干子技术
  ↓
按出现频次 + 性能提升排序
  ↓
提取 Top-3 子技术
  ↓
人工审阅 + 反方证据检查
  ↓
最终子技术列表
```

### 4.2 子技术排序规则

**优先级评分**：
```
子技术得分 = 出现频次 × 性能提升 × 反方风险系数

其中反方风险系数：
  - 低风险：1.0
  - 中风险：0.7
  - 高风险：0.4
```

**排序输出**：Top 3 子技术，按得分降序

### 4.3 子技术选型决策树

```
K×S 子技术选型
  │
  ├─ 第一层: 业务约束六问 → 锁定场景
  │
  ├─ 第二层: 第一性原理 → 找出"为什么"
  │
  ├─ 第三层: 现有 5-6 个子方法为何不行？
  │
  ├─ 第四层: 综合得分评分 → 量化决策
  │
  ├─ 第五层: 信源验证 → 论文支持
  │
  └─ 最终: 选 1 个子技术
```

## 五、v2.0 新增：反方证据库

> **v1 缺失**的反方证据，导致方法论"自我实现预言"

### 5.1 反方证据库结构

```json
{
  "counter_evidence": [
    {
      "direction": "KV×量化→2-bit",
      "history_failure": "过去 3 年 2-bit KV 量化论文 80% 在数学任务崩溃",
      "patent_risk": "DeepSeek MLA 部分专利覆盖",
      "resource_threshold": "需要 50+ GPU×月（大规模实验）",
      "team_mismatch": "需要 CUDA kernel 开发能力，团队只有 2 人",
      "reverse_scenario": "如果客户不要求 2-bit，1.5-bit 没有意义"
    },
    ...
  ]
}
```

### 5.2 反方证据评分标准

| 维度 | 1 分（低风险） | 2 分（中风险） | 3 分（高风险） |
|------|--------------|--------------|--------------|
| **历史失败风险** | 无失败案例 | 1-2 个失败 | 多次失败 |
| **专利壁垒** | 无专利 | 部分专利 | 完全被专利保护 |
| **资源门槛** | < 10 GPU×月 | 10-50 GPU×月 | > 50 GPU×月 |
| **团队不匹配** | 完全匹配 | 部分匹配 | 完全不匹配 |
| **反向场景** | 无反向场景 | 1-2 个反向 | 多场景反向 |

### 5.3 反方证据应用

```
课题评分 = 综合得分 × (1 - 反方风险比例)

其中：
  反方风险比例 = 反方得分 / 15

反方风险比例 0-33%：低风险，正常推进
反方风险比例 34-66%：中风险，需要风险缓解
反方风险比例 67-100%：高风险，必须有备选方案
```
