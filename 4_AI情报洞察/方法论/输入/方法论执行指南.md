# 方法论执行指南 v2.0

> 版本: v2.0 | 更新: 2026-06-28
> **v2.0 新增：历史回测机制 + 季度方法论复盘 + 评分者一致性测试 + 跨场景协同**

**用途**：将"瓶颈-假设-验证 因果推导法"转化为可操作的日/周/月/季/年执行清单
**核心问题**：谁在什么时间用什么工具做什么，输出是什么

## 二、执行时间表（v1 保留 + v2.0 增强）

### 2.1 日频（情报工程师）

```
【每日30分钟】
任务：从arXiv/GitHub采集12格新信号

工具：
  → arXiv API（按关键词搜索近24小时新论文）
  → GitHub Trending（按topic搜索新增仓库）
  → Twitter/知乎（技术讨论信号）

操作：
  1. 对12个格子运行arXiv关键词搜索
  2. 记录：新论文数量、GitHub新star、新闻事件
  3. 填入「12格月度趋势追踪表」
  4. v2.0 新增：检查 P2 课题的触发信号

输出：
  → 「12格日度信号记录.md」
  → 如果某格子单日出现重大突破（新论文>5篇或新GitHub>500star）→ 触发自更新警报

判断标准：
  □ 单格子日新增论文 > 5篇 → 标记"可能爆发"
  □ 出现工业集成公告 → 立即上报
  □ v2.0 新增：P2 课题的触发信号出现 → 升级 P1 评估
```

### 2.2 周频（情报工程师）

```
【每周1小时】
任务：汇总本周12格信号，更新月度趋势追踪表

工具：
  → 本地知识库（Obsidian）：周度汇总
  → 趋势计算：月均增速、顶会acceptance变化

操作：
  1. 汇总本周7天的日度信号
  2. 更新12格月度趋势追踪表：
     - 论文总数变化
     - 月均增速（增长/平稳/下降）
     - 新出现的GitHub仓库
  3. 对照自更新触发条件，判断是否需要触发评估
  4. v2.0 新增：检查 P2 课题的升级标准

输出：
  → 「12格周度趋势报告.md」
  → 如果触发条件满足 → 填写自更新警报
```

### 2.3 月频（课题规划负责人）

```
【每月2-4小时】
任务：更新矩阵数据、复盘课题进展、评估自更新需求

工具：
  → 12格月度趋势追踪表
  → 课题状态追踪表
  → 假设清单状态

操作：

【Part 1：矩阵数据更新】
  1. 更新12格论文数量（近3个月新增）
  2. 更新顶会acceptance（近一个顶会cycle）
  3. 重新评估前瞻判断（演进链是否需要更新）
  4. 重新计算综合星级（★5/4/3/2/1）
  5. 对比上月，判断哪些格子趋势发生了变化
  6. v2.0 新增：检查 P1 课题的进度和风险

【Part 2：课题复盘】
  7. 检查每个在研课题的假设验证状态
  8. 检查是否有假设被新论文/新数据证伪
  9. 评估失效保险的触发条件是否接近
  10. v2.0 新增：检查反方证据的实际情况

输出：
  → 「月度战略评估报告.md」（发给课题负责人）
```

## 三、v2.0 新增：历史回测机制（核心改进）

> **v1 缺失**的验证机制，导致方法论未经检验

### 3.1 回测方案

```
回测方案：
  1. 选择 N 个月前的方法论预测（推荐 N=3）
  2. 对比 N 个月后的实际发展
  3. 记录预测偏差（高估/低估/正确）
  4. 更新方法论参数

回测频次：
  - 季度回测：每季度末做一次
  - 年度回测：每年末做全面回测
```

### 3.2 回测模板

```markdown
## 季度回测报告 - [YYYY-QX]

### 一、预测 vs 实际对比

| 课题 | 当时优先级 | 当前状态 | 偏差分析 |
|------|----------|---------|---------|
| 课题 1 | P0 | 已完成 | ✓ 正确 |
| 课题 2 | P0 | 进展缓慢 | ↓ 低估难度 |
| 课题 3 | P1 | 已被其他团队完成 | ↓ 低估竞争 |
| 课题 4 | 未预测 | 突然爆发 | ⚠ 漏报 |
| 课题 5 | P0 | 失败 | ↓ 反方证据未充分 |

### 二、统计指标

- 预测准确率 = 正确数 / 总预测数 = X / Y = Z%
- 漏报率 = 漏报数 / 实际重要数 = X / Y = Z%
- 误报率 = 误报数 / 总预测数 = X / Y = Z%
- 漏报方向：[列出]
- 误报方向：[列出]

### 三、方法论更新

- 评分卡权重调整：
- 业务约束更新：
- 新增子技术：
- 新增反方证据检查：
```

### 3.3 回测准确率目标

```
- ≥ 70%：方法论可信，继续使用
- 50-70%：方法论需调整
- < 50%：方法论需大改
```

### 3.4 回测失败处理

```
如果回测准确率 < 50%：
  1. 立即停止使用方法论生成新课题
  2. 召开方法论复盘会议（72小时内）
  3. 找出回测失败的根因（评分卡问题？信源问题？约束问题？）
  4. 修订方法论
  5. 重新回测（用修订后的方法论）
  6. 准确率 ≥ 70% 后恢复使用
```

## 四、v2.0 新增：评分者一致性测试

> **v1 缺失**的评分验证，导致评分主观性无法量化

### 4.1 测试方案

```
方案：
  1. 让 3-5 个团队成员独立评分 25 个课题
  2. 计算 Krippendorff's alpha 系数
  3. 系数 < 0.6 表示评分一致性差，需要细化评分标准
```

### 4.2 测试时机

```
- 课题评分前（基础）：建立评分基线
- 季度复盘时（持续）：监控评分漂移
- 评分标准调整后（验证）：确认调整有效
- 团队成员变动时（更新）：新成员培训
```

### 4.3 一致性差时的处理

```
α < 0.4：方法论不可用，立即暂停
0.4 ≤ α < 0.6：一致性差，需要大改评分标准
0.6 ≤ α < 0.8：基本一致，需要小幅调整
α ≥ 0.8：高度一致，方法论可信
```

### 4.4 评分卡细化方法

```
对每个评分维度：
  1. 提供 3 个具体例子（1/2/3 分各一个）
  2. 提供"区分指南"（什么时候是 2 vs 3）
  3. 提供"决策树"（如何一步步确定分数）
  4. 团队培训（30 分钟）
```

## 九、常见问题

### Q1：情报工程师不在/休假怎么办？

```
→ 有备用人员：提前交接日度采集任务
→ 无备用人员：
  → 日度采集可以跳过（不会影响大局）
  → 周度汇总时补录即可
  → 月度评估必须按时完成
```

### Q2：两周验证失败率很高怎么办？

```
→ 检查验证设计：两周验证是否设计得太严格？
  → 验证的是"假设是否成立"，不是"整个方案是否可行"
  → 如果一个假设频繁失败，可能是方法论文档的趋势判断有问题

→ 检查方法论：
  → 某个格子的"空白"是真的还是假的？
  → 是否触发了自更新警报？

→ 如果某个方向的假设连续2次失败：
  → 升级为自更新警报，重新评估该方向是否还值得跟

v2.0 新增：
→ v2.0 新增：检查反方证据评分
  → 反方证据得分 ≥ 11 的课题失败率高是预期的
  → 准备备选方案
```

### Q3：多个课题同时触发失效保险怎么办？

```
→ 优先级排序：
  1. 哪个课题的失败影响最大？（公式中瓶颈最大的那个优先处理）
  2. 哪个课题的备选方向最清晰？（备选方向明确的优先处理）

→ 如果同时失败 > 2个课题：
  → 触发紧急会议（48小时内）
  → 重新评估整个课题体系是否需要重建
  → 可能触发方法论的季度更新
```

### Q4：自更新警报太频繁怎么办？

```
→ 调整触发阈值：
  → 单格子日新增论文：从 > 5篇 调整为 > 8篇
  → 月均增速：从 > 20% 调整为 > 30%

→ 如果仍然太频繁：
  → 说明情报系统过于敏感，需要重新校准判断标准
  → 这本身是一个方法论问题，需要记录到自更新日志

→ 如果太少（半年没触发一次）：
  → 检查方法论是否太保守
  → 或者情报采集频率是否太低
```

### v2.0 新增：Q5：评分者一致性差怎么办？

```
→ 立即暂停方法论使用
→ 细化评分标准（提供具体例子）
→ 团队培训
→ 重新测试一致性
→ α ≥ 0.6 后恢复使用
```

### v2.0 新增：Q6：历史回测准确率低怎么办？

```
→ 立即停止使用该方法论生成新课题
→ 召开方法论复盘会议（72小时内）
→ 找出回测失败的根因
→ 修订方法论
→ 重新回测（用修订后的方法论）
→ 准确率 ≥ 70% 后恢复使用
```

### v2.0 新增：Q7：反方证据成真怎么办？

```
→ 立即评估课题风险
→ 准备备选方案
→ 调整资源投入
→ 触发方法论更新
→ 写入"方法论自更新日志"
```

## 十三、红蓝对抗挑战具体化规则（v2.1 新增）

### 13.1 问题

## 十五、Kill Project 标准（v2.2 新增）

> 方法论不只讲"做什么"，还要讲"什么时候停止做"。

### 15.1 Kill 触发条件（满足任一即触发评审）

| 条件 | 说明 | 数据来源 |
|------|------|---------|
| **连续 2 季度无新论文** | 该方向学术停滞 | papers_meta 季度增量 |
| **两周验证连续 2 次失败** | 假设不可行 | 课题状态追踪表 |
| **失效保险触发且备选也失败** | Plan A 和 Plan B 都不行 | 失效保险记录 |
| **颠覆性替代出现** | 新架构完全取代（如 Mamba 取代 Transformer） | 每季度趋势扫描 |
| **资源 ROI 持续下降** | 连续 2 季度 ROI <50% | ROI 追踪表 |

### 15.2 Kill 流程

```
触发条件满足
  ↓
课题负责人提交 Kill 申请（含数据和理由）
  ↓
课题规划负责人评审（48h 内）
  ↓
决策: □ Kill（归档） □ 缓期（给最后一次机会） □ 继续（触发条件误报）
  ↓
如果 Kill:
  - 课题状态改为"已归档"
  - 代码/文档/数据归档到 `_archive/`
  - 释放资源给其他课题
  - 每半年复查一次（防止过早 Kill）
```

### 15.3 归档不等于删除

归档的课题保留追踪：
- 每半年扫描一次该方向是否有"复活信号"（新论文/新工业落地）
- 如果出现复活信号 → 重新评估是否重启

## 十六、论文三级筛选标准（v2.2 新增）

> 3876 篇论文不可能全读。定义筛选优先级。

### 16.1 三级标准

| 级别 | 标准 | 处理方式 | 数量上限 |
|------|------|---------|---------|
| **S 级（必读）** | 评分≥8 + 有代码 + 顶会（ICLR/NeurIPS/ICML/OSDI） | 精读全文 + 复现代码 | ≤5 篇/月 |
| **A 级（选读）** | 评分 6-8 或 P0 格子新论文 | 读摘要+结论+图表 | ≤20 篇/月 |
| **B 级（扫一眼）** | 其余被分类的论文 | 标题+关键词扫描 | ≤50 篇/月 |

### 16.2 升级规则

```
B 级 → A 级: 被多篇 S 级论文引用 / 出现在 P0 格子趋势中
A 级 → S 级: 评分升至 8+ / 被工业采用（GitHub star>500）
```

### 16.3 淘汰规则

```
B 级论文 3 个月内:
  - 未被引用 → 归档（不删除，移出活跃列表）
  - 被引用 → 升级到 A 级
```

## 十七、课题生命周期（v2.2 新增）

> 课题不是"做完就结束"——有持续维护期。

### 17.1 完整生命周期

```
验证期（2 周）→ 实施期（8-10 周）→ 收尾期（2 周）→ 维护期（持续）
```

### 17.2 维护期要求

| 项目 | 要求 | 频率 |
|------|------|------|
| 代码兼容性 | 新模型/新框架版本是否兼容 | 每季度 |
| 文档更新 | README + 设计决策记录是否过时 | 每季度 |
| 知识转移 | 维护人 + 备份维护人 | 持续 |
| 技术债务 | Tech Debt Log 更新 | 每季度 |

### 17.3 课题归档清单（收尾时必须完成）

```
□ 代码仓库 URL + README（含运行方式）
□ 关键设计决策记录（为什么这么选，不是另一种）
□ 已知问题清单（Tech Debt Log）
□ 维护人 + 备份维护人
□ 监控指标（上线后看什么）
□ Kill 标准（什么时候应该下线）
```
