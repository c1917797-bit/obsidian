## 课题一：面向 Agent 场景的 LLM 跨轮 KV 共享机制

**业务约束（业务驱动方法）**：
- Q1（多卡 vs 单卡）：✅ 多卡 MoE 架构
- Q2（序列长度）：✅ 128K-1M 长上下文
- Q4（并发）：✅ Agent 多轮 10-50 轮
- Q5（精度）：≤1% 精度损失
- **约束过滤**：K 必要 + 多轮场景强需求

**关键挑战**：Agent 多轮对话中，前 N 轮的 KV 在后续轮次仍需使用。**当前系统每轮都从头计算 KV**，10 轮对话 = 10x 算力浪费。完全研究空白：所有现有 KV 压缩工作都假设单轮场景。

**技术目标**（引用目标.md 公式）：

- 跨轮 KV 命中率 ≥ **60%**
- 多轮 TPOT 降低 **40%**（公式五：TPOT = (T_calc_decode + S_input × T_mem) + T_comm × (1 - θ)）
- C_max 提升 **30%**（公式二：C_max = min(C_V, C_gpu, C_comm)）
- 任务完成率保持不变

**关键技术**：

1. **跨轮 KV 重要性评分（轮次感知）**
   每轮结束时评估所有 KV 的"未来价值"，给每个 KV 打分；分数低的轮次 KV 优先淘汰。

2. **跨轮 KV 共享池（多轮复用）**
   建立跨轮 KV 共享池（与 vLLM Prefix Cache 概念类似但粒度更细），按 query 相似度匹配复用。

3. **轮次衰减机制（控制内存增长）**
   跨轮 KV 随轮次增加按指数衰减（round N 的 KV 保留概率 0.9^N），避免内存无限增长。

**对象×方法**：K × S（KV × 稀疏化）

**综合得分**（技术驱动方法评分卡）：
- 技术深度：3/3（创新性强，第一性原理清晰）
- 工程影响：3/3（Agent 场景核心瓶颈）
- 趋势强度：2/2（Agent 是 2026 爆发点）
- 行业影响：2/2（Agent 跨场景通用）
- **综合得分：3×3×2×2 = 36 → 10分**（进入战略分析）

**代码状态**：❌ 无（全新方向，需从零开发）

## 课题二：MoE 分布式推理专家参数量化与通信压缩

**业务约束**：
- Q1：✅ 多卡 MoE（DeepSeek-V3/Qwen3-Max）
- Q2：✅ 128K+ 长上下文
- Q3：✅ TPOT 降低 30%
- Q4：✅ 高并发（数十路）
- Q6：✅ MoE 架构
- **约束过滤**：C 必要 + MoE 必选

**关键挑战**：MoE 模型每个 Token 仅激活少数专家（Top-2/Top-4），但需要 All-to-All 路由通信。在 128K 上下文 + 64 并发生产环境下，**通信占比达 40-60%**。现有方案"全复制所有专家"（用空间换通信）实际是低效的。

**技术目标**（引用目标.md 公式）：

- 跨卡 All-to-All 通信量降低 **50%-80%**（公式三：T_comm = T_allreduce × N_TP + T_p2p × N_PP + T_expert × N_MoE）
- 单 Token 推理时延降低 **25%-40%**（公式五：TPOT）
- TPS 提升 **1.5x**（公式七：TPS ≈ 1/TPOT × Parallelism_Degree）
- 模型精度损失 ≤ **1%**

**关键技术**：

1. **专家参数 INT4 量化 + 动态精度切换（通信减量）**
   对 All-to-All 传输中的专家参数做 INT4 量化；同时保留本地"影子副本"为关键专家提供 FP8/FP16 fallback。

2. **路由感知的稀疏通信（流量减负）**
   基于路由表预测哪些节点间通信最频繁（hot pair），仅对这些路径做 FP8 高频传输。

3. **通信-计算重叠 + 量化协同调度（延迟隐藏）**
   将量化-通信-反量化流水化，与专家计算并行。

**对象×方法**：C × Q（通信 × 量化）

**综合得分**：
- 技术深度：3/3（通信-计算协同创新）
- 工程影响：3/3（MoE 核心瓶颈）
- 趋势强度：2/2（DeepSeek-V3 推动）

- **综合得分：3×3×2×2 = 36 → 10分**

## 课题三：RoPE 频域感知的低比特 KV Cache 量化

**业务约束**：
- Q1：✅ 多卡
- Q2：✅ 128K+ 长上下文
- Q3：✅ TPOT 降低
- Q5：≤1% 精度损失
- Q6：✅ MoE 架构（RoPE 普遍）
- **约束过滤**：K 必要 + 长上下文强需求

**关键挑战**：所有主流 LLM（Llama/Qwen/DeepSeek）都使用 RoPE 旋转位置编码，但现有 KV 量化方法把 Key 当"普通向量"处理，**忽略了 RoPE 频域能量分布的极端不均**。均匀比特分配在数学推理任务上直接崩溃（AIME 2024 = 0 分）。Block-GTQ (2026) 首次揭示这一现象，K2V2 配置 AIME24 达 **51.7**（接近 FP16 的 54.2），但**框架集成（vLLM/SGLang）仍为空白**。

**技术目标**：

- KV 比特降至 **2-bit**（K2V2），AIME24 准确率 ≥ **50**
- vLLM / SGLang 主线 PR 合并
- 通用数学/代码任务精度损失 ≤ **2%**
- TPOT 降低 **30%**（KV 减少带来的访存降低）

**关键技术**：

1. **RoPE 频域分块 + 能量感知比特分配（基础方案）**
   将 KV 按 RoPE 频域块分组，每个块独立评估能量分布；高能量块分配 4-bit，低能量块可降至 1-bit；总平均 2.5-bit。

2. **任务感知比特预算分配（数学/代码/对话差异化）**
   推理类任务对 RoPE 高频分量敏感，分配更多比特；对话类任务采用 RoPE-全频率均衡策略。

3. **框架级集成：vLLM/SGLang 算子融合（工程落地）**
   将频域分块 + 比特分配实现在 CUDA kernel 中，与 PagedAttention / RadixAttention 兼容。

**对象×方法**：K × Q（KV × 量化）

**综合得分**：
- 技术深度：3/3（频域感知，第一性原理）
- 工程影响：3/3（vLLM/SGLang 集成）

- 行业影响：2/2（所有 RoPE 模型受益）
- **综合得分：3×3×2×2 = 36 → 10分**

**代码状态**：❌ 无（需自研 CUDA kernel）

## 课题四：Dustin 长上下文投机解码稀疏验证加速

**业务约束**：
- Q2：✅ 128K+ 长上下文
- Q3：✅ TTFT 降低
- Q5：≤1% 精度损失
- **约束过滤**：K 必要 + 投机解码是补充

**关键挑战**：长上下文（128K+）+ 投机解码场景下，**87.5% 的验证时间花在 KV 加载而非实际计算**（Dustin, ICML 2026）。验证阶段需加载完整 KV Cache，导致投机解码的加速比被严重削弱（理论上 10x，实际只有 2-3x）。

**技术目标**：

- 验证阶段 self-attention 加速 **>20x**（Dustin 论文 27.85x）
- 投机接受率保持 ≥ **0.85**
- 端到端 TTFT 降低 **40%**（公式四：TTFT = (S_input × T_calc + T_comm) × (1 - η) + T_queue × (1 - λ)）
- E2E 时延降低 **35%**（公式六：E2E = TTFT + (N_out-1) × TPOT）

**关键技术**：

1. **验证阶段 KV 预取与缓存（I/O 减负）**
   验证阶段需要全部 KV，但其中 80% 与上一次投机阶段相同；将这些"热 KV"缓存在 L2 cache，验证时只加载"冷 KV"。

2. **稀疏验证策略（计算减负）**
   投机解码的"草稿 token"已通过小模型验证，**大模型验证时可只对预测最不确定的 token 加载完整 KV**。

3. **分布式投机解码协同（多节点扩展）**
   在多节点部署下，验证阶段涉及跨节点 KV 通信；通过 gossip 协议同步热 KV。

**对象×方法**：K × S（KV × 稀疏化） + S × G（推理状态 × 通用优化）
