## 零、年度战略目标：每年优于业界 30%（v2.2 新增，最高优先级）

> **这是方法论的最高层目标——所有课题、所有报告、所有指标的终极锚点。**

### 0.1 目标定义

```
每年，我们的推理系统综合竞争力必须优于业界平均水平 30%。

"综合竞争力" = 加权平均(时延, 吞吐, 成本, 精度)

权重:
  时延 (TTFT/TPOT): 30%
  吞吐 (TPS): 30%
  成本 ($/1M tokens): 30%
  精度 (MMLU/LongBench): 10%（不低于业界平均即可，不要求超越）
```

> ⚠️ **权重是场景自适应的**（v2.2 修正），见 §0.6。

**每个课题的量化目标必须满足**：

```

示例:
  业界 TPOT = 30ms → 我们目标 ≤ 21ms（30ms × 0.7）
  业界 TPS = 100 → 我们目标 ≥ 130（100 × 1.3）

**不满足 30% 的课题**：
- 如果某课题只能提升 15%（不到 30%），必须说明：
  1. 为什么达不到 30%？（技术天花板？资源限制？）

**使用规则**：每份报告在 §2.1 标注本课题的场景权重，然后按此权重计算加权竞争力。

## 一、核心指标定义

在 Agent 时代多卡推理场景下，推理效率竞争力体现在**四个核心维度**上：

| 指标 | 目标 | 说明 |
| -------- | ------------------- | ------------------------------- |
| **推理时延** | 加速 **1.5 倍**（时延降低 33%） | 端到端时延 = TTFT + (N_out-1) × TPOT |
| **系统吞吐** | 提升 **2 倍** | TPS = C × min(1/TPOT, N_out/T_e2e) |
| **并发会话数** | 提升 **2 倍** | C_max = f(V, S, P, N_gpu) |
| **模型精度** | 损失 **≤1%** | 以 LongBench/AgentBench 任务相关评测集为基准 |

> **⚠️ 重要**：时延优化与吞吐优化存在 **Trade-off**，需在系统设计时权衡（详见第四章）。

## 三、公式体系（v1.1 保留）

### 3.1 时延拆解

端到端推理时延由 Prefill 和 Decode 两个阶段组成：

| 子指标 | 定义 | 构成 | 对应的瓶颈 |
|--------|------|------|-----------|
| **TTFT** | 首 Token 时延，反映系统"反应速度" | T_prefill + T_sched | Prefill 计算量大、排队时延长 |
| **TPOT** | 逐 Token 时延，决定内容生成"流畅度" | T_decode + T_comm | KV 访存慢、MoE 通信阻塞 |

#### 3.1.1 吞吐拆解

系统吞吐由并发度和单 Token 时延共同决定：

```
TPS = B / TPOT,  B = (M_total - M_weights) / M_KV
```

- **B**：单卡最大可承载并发会话数
- **M_KV**：单请求 KV Cache 显存占用

---

### 3.2 公式一：KV Cache 显存占用

```
KV = 2 × L × H × D × S × P × C
```

| 变量 | 含义 | 单位 | 规划干预策略 |
| :--- | :--- | :--- | :--- |
| **L** | Transformer 网络层数 | 层 | 模型结构固定 |
| **H** | 注意力头数量 | 个 | 模型结构固定 |
| **D** | 单注意力头维度 | 维 | 模型结构固定 |
| **S** | **有效上下文长度（即 S_input）** | Tokens | **核心干预变量** |
| **P** | 数据精度位宽（Precision） | Byte | 辅助优化 |
| **C** | 系统并发会话数 | 个 | 受显存总量限制的因变量 |

> **扩展：MoE 模型**（v2.1 修正）
>
> **说明**：MoE 模型的 KV Cache 形状与 Dense 相同（每个 token 都经过相同的 attention heads），因此 KV 显存占用公式不变。MoE 的影响体现在：
>
> 1. **权重显存 V_backbone 大幅增加**（E_total × V_per_expert 替代单 FFN）
> 2. **专家通信开销 T_comm_expert**（dispatch + combine）
>
> **MoE 场景下应修正 V_backbone 和 T_comm，而不是 KV 公式：**
> ```
> # KV Cache 公式本身不变（attention 路径一致）
> KV_MoE ≈ KV_Dense = 2 × L × H × D × S × P × C
>
> # 但 V_backbone 需要修正（v2.1 修正）
> V_backbone_MoE = V_dense_backbone + V_experts
>               = V_dense_backbone + E_total × V_per_expert
>
> # T_comm 需要加上专家通信（v2.1 修正）
> T_comm_MoE = T_comm_Dense + T_expert_dispatch + T_expert_combine
>            = T_comm_Dense + α × E_active × (T_p2p + T_allreduce)
>
> # 修正后 C_max:
> C_max_MoE = min(C_V_MoE, C_gpu, C_comm_MoE)
>           = min((V_total - V_backbone_MoE) / (2 × L × H × D × S × P), C_gpu, C_comm_MoE)
> ```
>
> **参数定义**：
> - `E_total`: 专家总数（如 DeepSeek-V3: 256）
> - `E_active`: 每个 token 激活的专家数（如 8）
> - `V_per_expert`: 单个专家的显存
> - `α`: 路由偏置系数（0 < α ≤ 1，反映负载不均衡）
>
> **v2.0 原公式的问题**：`KV_MoE = 2 × L × H × D × S × P × C × (1 + α × E_active / E_total)` 中 `E_active/E_total` 与 KV 无关，混淆了 FFN 专家数与 Attention KV 的关系。

---

### 3.3 公式二：并发会话数

```
C_max ≈ (V_total - V_backbone) / (2 × L × H × D × S × P)
```

> **v1.1 补充**：
> ```
> C_max = min(C_V, C_gpu, C_comm)
>
> 其中：
>   C_V     = (V_total - V_backbone) / (2 × L × H × D × S × P)    // 显存约束
>   C_gpu   = N_gpu / G_per_session                                  // GPU 数量约束
>   C_comm  = Bandwidth_effective / (T_comm_per_token × R)           // 通信带宽约束
> ```

#### 3.3.1 C_gpu 详细推导（v2.1 新增）

```
C_gpu = floor(N_gpu / G_per_session)

其中：
  N_gpu          = 集群总 GPU 数
  G_per_session  = 单会话所需 GPU 数 = TP_degree × PP_degree

  并行策略示例：
    - 单卡推理：        G_per_session = 1
    - TP=4 推理：       G_per_session = 4
    - TP=8 + PP=2：     G_per_session = 16
    - MoE EP=8 + TP=4： G_per_session = 32 (专家并行 8 路复制到 4 个 TP 组)

  C_gpu 是硬上限，受硬件采购预算决定。
```

#### 3.3.2 C_comm 详细推导（v2.1 新增）

```
C_comm = floor(Bandwidth_effective × η / (T_comm_per_token × R_per_session))

其中：
  Bandwidth_effective  = 单次通信的有效带宽（Bytes/s）
  η                    = 通信效率（0 < η ≤ 1，通常 NVLink ≈ 0.7, IB-RDMA ≈ 0.5）
  T_comm_per_token     = 单 token 的通信时间（s）
  R_per_session        = 单会话的有效并行 token 数（含 micro-batch）

  T_comm_per_token 与并行策略的函数关系：
    - TP only:    T_comm ≈ (TP-1) / TP × AllReduce(KV_size) / BW
    - PP only:    T_comm ≈ (PP-1) / PP × P2P(activation) / BW
    - MoE EP:     T_comm ≈ dispatch + combine ≈ 2 × E_active × hidden_size / BW
    - TP+PP+EP:   T_comm ≈ max(TP_AllReduce, PP_P2P, MoE_dispatch)

  通信硬件参考（v2.1 补充）：
    - NVLink 4.0 (H100):  900 GB/s (双向)
    - NVLink 3.0 (A100):  600 GB/s (双向)
    - IB HDR (200 Gbps):  25 GB/s
    - IB NDR (400 Gbps):  50 GB/s

  通信瓶颈判断（v2.1 新增）：
    if C_comm < min(C_V, C_gpu)  → 系统是通信受限 → 优化方向: 压缩/拓扑/算法
    if C_V < min(C_gpu, C_comm)  → 系统是显存受限 → 优化方向: KV压缩/量化
    if C_gpu < min(C_V, C_comm)  → 系统是GPU数受限 → 优化方向: 扩硬件/减并行度
```

#### 3.3.3 典型场景示例（v2.1 新增）

| 场景 | 模型 | N_gpu | TP×PP×EP | C_V | C_gpu | C_comm | C_max | 瓶颈 |
|------|------|-------|---------|-----|-------|--------|-------|------|
| 7B 单卡 | Llama-7B | 1 | 1×1×1 | 50 | 1 | ∞ | **1** | GPU数 |
| 70B TP=8 | Llama-70B | 8 | 8×1×1 | 8 | 1 | 16 | **1** | GPU数 |
| 405B TP=8 PP=2 | Llama-405B | 16 | 8×2×1 | 2 | 1 | 8 | **1** | GPU数 |
| MoE-256 TP=4 EP=8 | DeepSeek-V3 | 32 | 4×1×8 | 4 | 1 | 2 | **1** | **通信** |
| 长上下文 1M | Llama-3-8B-1M | 8 | 8×1×1 | 2 | 1 | 4 | **1** | GPU数+显存 |

### 3.4 公式三：跨卡通信开销

```
T_comm = T_allreduce × N_TP + T_p2p × N_PP + T_expert × N_MoE
```

---

### 3.5 公式四：TTFT

```
TTFT = (S_input × T_calc + T_comm) × (1 - η) + T_queue × (1 - λ)
```

---

### 3.6 公式五：TPOT

```
TPOT = (T_calc_decode + S_input × T_mem) + T_comm × (1 - θ)
```

---

### 3.7 公式六：E2E 端到端时延

```
E2E = TTFT + (N_out - 1) × TPOT
```

---

### 3.8 公式七：TPS

```
TPS = (C × N_out) / T_total  ≈ C × R_out
TPS ≈ 1/TPOT × Parallelism_Degree
```

## 四、时延 vs 吞吐 Trade-off 分析

### 4.1 矛盾的本质

| 目标 | 优化方向 | 副作用 |
|------|---------|-------|
| **低时延** | 减少 S_input、减少 N_out | 可能降低答案质量 |
| **高吞吐** | 增加并发 C | TPOT 上升（资源竞争） |

### 4.2 调度策略矩阵

| 策略 | 目标 | C | TPOT | 适用场景 |
|------|------|:---:|:----:|---------|
| **低延迟优先** | Min TTFT | 低 | 低 | 实时交互 |
| **高吞吐优先** | Max TPS | 高 | 中 | 批处理 |
| **均衡模式** | Min E2E@HighTPS | 中 | 中 | 通用场景 |

### 4.3 推荐配置

| 应用场景 | 策略 | 目标 TPS | 目标 TTFT | 目标 TPOT |
|---------|------|---------|-----------|-----------|
| 实时对话 | 低延迟优先 | >10 tok/s | <500ms | <50ms |
| Agent 任务 | 均衡模式 | >50 tok/s | <1s | <30ms |
| 批量生成 | 高吞吐优先 | >200 tok/s | <3s | <20ms |

## 七、v2.0 新增：反方证据公式（重要！）

> **v1.1 缺失**的反方证据，导致方法论"自我实现预言"

**每个课题目标必须回答反方问题**：

```
反方得分 = 历史失败风险 + 专利壁垒 + 资源门槛 + 团队不匹配 + 反向场景

其中：
  - 历史失败风险 (0-3)：过去 3 年类似方向失败案例数
  - 专利壁垒 (0-3)：是否被 DeepSeek/Google 等专利保护
  - 资源门槛 (0-3)：GPU×月需求（0=<10, 1=10-50, 2=50-100, 3=>100）
  - 团队不匹配 (0-3)：现有团队能力差距（0=完全匹配, 3=完全不匹配）
  - 反向场景 (0-3)：在什么场景下目标是错的
```

**反方得分判断**：
- 0-5 分：低风险，正常推进
- 6-10 分：中风险，需要风险缓解
- 11-15 分：高风险，必须有备选方案

**反方得分≥10 的课题必须有"备选方案"**：
- 备选方案 1：技术路径不同但目标相同
- 备选方案 2：降低目标但风险更小
- 备选方案 3：完全放弃，转向其他方向

## 九、v2.0 新增：历史回测机制（重要！）

> **v1.1 缺失**的验证机制，导致方法论未经检验

**每季度进行历史回测**：

```
回测方案：
  1. 选择 N 个月前的方法论预测
  2. 对比 N 个月后的实际发展
  3. 记录预测偏差（高估/低估/正确）
  4. 更新方法论参数

回测指标：
  - 预测准确率：实际发展与方法论预测一致的比率
  - 漏报率：方法论没预测到但实际重要的方向
  - 误报率：方法论预测但实际不重要
```

**回测准确率目标**：
- ≥70%：方法论可信，继续使用
- 50-70%：方法论需调整
- <50%：方法论需大改

**回测模板**：
```markdown
## 季度回测报告

### 预测 vs 实际对比

| 课题 | 当时优先级 | 当前状态 | 偏差分析 |
|------|----------|---------|---------|
| 课题 1 | P0 | 已完成 | ✓ 正确 |
| 课题 2 | P0 | 进展缓慢 | ↓ 低估难度 |
| 课题 3 | P1 | 已被其他团队完成 | ↓ 低估竞争 |
| 课题 4 | 未预测 | 突然爆发 | ⚠ 漏报 |

### 方法论更新
- 评分卡权重调整
- 业务约束更新
- 新增子技术
```

### 10.2 目标可达性检查

| 目标 | 前置条件 | 反方风险 | 时间窗 |
|------|---------|---------|--------|
| 时延降低 33% | S_input 压缩 + T_comm 减少 | 高（已被多次失败） | 中期 |
| 吞吐提升 2x | C_max 翻倍 + TPOT 不显著上升 | 中 | 中期 |
| 精度损失 ≤1% | 量化方案验证 + 并发折扣测试 | 低 | 短期 |

### 10.3 监控指标

| 类别 | 指标 | 告警阈值 | **新增：反方信号** |
|------|------|---------|-----------------|
| **时延** | TTFT, TPOT, E2E | P99 > 目标 1.5x | 竞争对手突破时延极限 |
