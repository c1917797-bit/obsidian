## ★★★ SCD — Semantic Cache Distillation（跨异构模型 KV 传输压缩）

**论文**：Semantic Cache Distillation: Efficient State Transfer via Reuse and Selective Patching
**ID**：arXiv:2606.07684 | Qianli Ma, Zhiqing Tang, Hanshuai Cui, Zhi Yao, Weijia Jia
**机构**：华为诺亚方舟 + 北京大学 + 香港城市大学
**发表**：2026-06-05 | **ICML 2026**

### 问题：Disaggregated Serving 的双重通信瓶颈

**背景架构**：

```
Prefill（Producer, Device A）→ KV 传输（跨设备）→ Decode（Consumer, Device B）
```

两个核心问题：

**① 传输开销（Transmission Overhead）**

KV cache 大小：每个 token 约 320 KiB（以 GQA 风格 70B 模型为例）
- 128K token context → ~40 GB KV cache
- 在低带宽互连上，传输时间直接主导 TTFT

**② 语义漂移（Semantic Drift）**

Producer 和 Consumer 模型权重不同时（基础模型 → 微调模型 / Draft → Verifier），表征空间不同：
- 直接复用 Producer 的 KV 给 Consumer → 表征不匹配 → 误差逐层累积 → 生成质量下降
- 全量重算则失去 disaggregation 的延迟收益

### 核心挑战

| 方法 | 问题 |
|------|------|
| 原始 KV 传输 | 带宽瓶颈，带宽受限下 TTFT 受限 |
| 直接复用 | 语义漂移累积，质量下降 |
| 选择性重算（DroidSpeak）| 二元决策（重算 vs 复用），刚性的权衡 |
| 现有压缩方法 | 假设 producer/consumer 共享相同权重，只适用于 intra-model |

### SCD 解决方案：两个互补机制

**① Reuse — 低秩重建（带宽效率优先）**

- 大部分层在 producer 和 consumer 之间有高兼容性（shared architecture）
- 用**低秩投影**从 producer 表征重建 consumer 表征
- 大幅降低传输带宽需求
- 公式：给定 producer cache C_A，用低秩投影 P 重建 consumer 空间表征

**② Patch — 选择性补丁（语义对齐优先）**

- 少量关键层（transition layers）导致显著语义漂移
- 在这些层预测归一化 pre-attention 输入
- 截断误差传播，无需完整重算
- 区别于 DroidSpeak 的二元决策（reuse raw vs recompute）：SCD 做的是**选择→变换**（selection → transformation）

### 关键数据

| 指标 | 结果 |
|------|------|
| TTFT 提升 | **2.65×**（vs oracle consumer prefill）|
| 质量损失 | 生成质量在 oracle 的 **5% F1** 以内 |
| Pareto 前沿 | 在质量-延迟 Pareto 前沿上超越量化 + 选择性重算基线 |

### 理论贡献

**异构状态传输形式化**：
- 定义了 cache reuse 在表征不匹配下的形式化问题
- 证明了为何原始传输和静态压缩在 disaggregated 设置下失效

### 产业意义

第一个系统解决**跨模型 disaggregated serving** KV 传输问题的论文。对应生产场景：shared-prefill + specialist decode 的服务架构（如在线服务对通用基础模型做 shared prefill，路由到多个微调 specialist consumer）。

## ★★ Gimbal — 前端+后端跨层协同调度

**论文**：Coordinated Scheduling for MoE LLM Serving
**ID**：arXiv:2606.15177 | Yifan Sun, Zhexiang Zhang 等
**机构**：墨尔本大学 + 莫纳什大学 + 中国科学院深圳先进技术研究院
**发表**：2026-06-13 | **ACM ATC 2026**

### 问题：MoE 调度的两层分离困境

**MoE Serving 架构**：

```
前端路由器 → 多个 Backend 推理引擎（DP replication）
                      ↓
              每个引擎内部：Attention（DP）+ MoE Layers（EP）
                      ↓
              All-to-All 通信（跨 GPU expert 路由）
```

**两层分离问题**：

| 层级 | 现有方法 | 致命缺陷 |
|------|---------|---------|
| **前端调度器** | 粗粒度请求计数（Round-Robin / 请求数）| 无法感知 token 级负载、KV cache 压力、后端 MoE 压力 |
| **后端 Expert 均衡器** | 聚合 expert 激活计数（EPLB-style）| 无法感知请求来源相关的 expert 流量 |

**为什么分离是致命的**：

```
请求分配给某 DP 引擎 → 该请求的 token 路由到特定 experts
                        ↓
        DP 引擎选择决定了 MoE All-to-All 通信的起点
        Expert 放置决定了 selected experts 是否 local/remote
```

请求计数调度无法捕获：
- Token 级负载
- 后端 MoE 压力
- 来源相关的跨 GPU expert 流量

### Gimbal 两部分设计

**① 细粒度 DP-Engine 调度器**

使用在线后端压力信号动态分发：
- 运行时 + 等待的 prefill tokens
- KV Cache 使用量
- 队列积压
- **MoE Expert 压力**

**Prefill-aware 队列排序**：
- Shortest-Job-First（SJF）风格 + aging
- 减少大 prefill 请求导致的 head-of-line blocking
- **无需输出长度预测**

**② Expert 放置 + 负载均衡**

收集在线 source-DP-to-expert 路由统计：
- Expert 负载
- **来源感知通信成本**（source-aware communication）
- 迁移稳定性

用 **MINLP（混合整数非线性规划）** 启发式联合优化 expert 放置。

### 关键数据

vs vLLM SOTA：

| 指标 | 提升 |
|------|------|
| 平均 TTFT 降低 | **42.9%** |
| 平均 TPOT 降低 | **33.3%** |
| 高负载请求吞吐量提升 | **3.0%** |
| P99 TTFT 降低 | **44.3%** |

###  ablation 验证

协同优化（DP 调度 + 来源感知 expert 放置）> 分别独立启用两个优化。

## ★★ FlexNPU — 透明 NPU 虚拟化 + 动态 PD 协同定位

**论文**：FlexNPU: Transparent NPU Virtualization for Dynamic LLM Prefill-Decode Co-location
**ID**：arXiv:2606.04415 | 华为
**发表**：2026-06-08

### 问题：静态 PD Disaggregation 的反模式

**Prefill vs Decode 的资源互补性**：

| 阶段 | 资源特征 |
|------|---------|
| Prefill | 计算密集型（Compute-bound）|
| Decode | 内存带宽约束 + KV Cache 访问 |

**静态 PD Disaggregation 的问题**：
- 减少阶段干扰，但引入资源不均衡
- 不必要的数据移动开销

**现有 NPU 部署问题**：
- 物理设备直接暴露给应用
- 无法运行时控制调度
- 无法适应 phase-level 工作负载特性

### FlexNPU 解决方案

**透明用户空间虚拟化架构**：

```
应用（ unmodified）
    ↓ AscendCL API
FlexNPU（per-device daemon）
    ↓
物理 NPU 设备
```

**关键特性：无需修改模型代码 / AI 框架 / NPU 驱动**

- 在 AscendCL API 层拦截
- 通过 per-device daemon 路由 NPU 操作
- 解耦应用与物理设备

**动态 PD Co-location**：
- 根据 prefill 和 decode 的互补资源特性**动态调整调度**
- 运行时在两者之间适配
- 而非静态分配

### 关键数据

DeepSeek-R1 @ 384-card Ascend 910C：

| 配置 | 结果 |
|------|------|
| vs 静态 PD Disaggregation | 吞吐量提升 **5.15%** 和 **26.33%** |
| vs 静态 PD Co-location | TTFT 降低 **92%**，TPOT 基本不变 |

Qwen2.5-7B @ 单卡：
- 无推理开销（vs 直接 NPU passthrough）
- 某些场景吞吐量甚至轻微提升

## ★★ CloudMoE — 本地 MoE 达到云级 SLO

**论文**：Achieving Cloud-Grade SLOs for Local Mixture-of-Experts Inference through CPU-GPU Hybrid Design
**ID**：arXiv:2606.10493
**发表**：2026-06 | **OSDI 2026**（录用）

### 问题：本地 MoE 推理的四大质量差距

| 维度 | 问题 | 云级目标 |
|------|------|---------|
| 模型质量 | 必须用量化/蒸馏/路由缩减版 | 完整精度 |
| Prefill TTFT | >30s（12K+ tokens）| 32K / 30s |
| Decode 吞吐 | <20 tokens/s | 基准水平 |
| 并发质量 | 混合 workload 质量差 | <15% 延迟增加 |

### 根因分析

**Decode 瓶颈**：主要受 CPU 侧带宽效率限制

KTransformers 的数据：
- 74% CPU 时间
- 20.4B 激活 MoE 参数
- 实际带宽利用率仅 ~50%（nominal aggregate DDR5）
- 16 tokens/s → 需要达到 ≥20 tokens/s

**Prefill 瓶颈**：消费级 GPU VRAM 限制

**五大解决方案**：

**① SLP — Stream-Loading Prefill**

执行模型：
- 突破消费级 GPU VRAM 限制
- 最大化 GPU 利用率
- CPU 协助下 stream-load prefill

效果：吞吐量 **1,200 tokens/s**，32K prompt 30s 内 TTFT

**② DSLP — 分布式 SLP + SmallEP**

- 多 GPU 本地 prefilling
- SmallEP：针对小 expert-parallel size 优化的专家并行
- 双 RTX 5090：吞吐量 **1,800 tokens/s**，45K prompt 30s 内

**③ 节点内 PD Disaggregation**

- 零拷贝共享模型权重
- 双 batch attention-MoE overlap 方案
- 并发延迟增加 <15%，吞吐量 +50%

**④ AVX-512 FP8 GEMV Kernel**

- 原生 CPU FP8 MoE 推理
- CPU 延迟降低 **4-5×**
- 带宽利用率显著提升

**⑤ 细粒度 CPU 并行**

- 最小化跨插槽通信和同步开销
- 融合量化特定操作
- INT4 DeepSeek-R1：**28 tokens/s**（vs KTransformers 22 tokens/s，+27%）
- FP8 DeepSeek-R1：**21.5 tokens/s**

### 关键数据总览

| 指标 | 结果 |
|------|------|
| DeepSeek-R1 INT4 Decode | **28 tokens/s** |
| DeepSeek-R1 FP8 Decode | **21.5 tokens/s** |
| Prefill 吞吐（SLP）| **1,200 tokens/s** |
| Prefill 吞吐（DSLP，双卡）| **1,800 tokens/s** |
| 32K TTFT | **<30s** |
| 45K TTFT（双卡）| **<30s** |
| 并发延迟增加 | **<15%** |

## ★★ NetKV — 网络拓扑感知的 Decode 实例选择

**论文**：Network-Aware Decode Instance Selection for Disaggregated LLM Inference
**ID**：arXiv:2606.03910 | Mubarak Ojewale 等
**发表**：2026-06-02

### 问题：KV 传输在 TTFT 预算中的核心角色

**Disaggregated LLM 推理的 KV 传输成本**：

| 配置 | 数据 |
|------|------|
| 128K Llama-3-70B 请求 | ~40 GB KV cache |
| TP=4 分片 | 每对 GPU ~10 GB |
| 25 Gbps RDMA 链路 | 每对 ~3.2s 传输时间 |

传输时间直接进入 TTFT 预算——选择哪个 decode 实例决定了多少预算被数据移动消耗。

### 现有调度器的盲区

| 系统 | 调度信号 | 缺失 |
|------|---------|------|
| DistServe | 同节点偏好 | 无 per-request 网络信号 |
| Mooncake | 缓存匹配 + 实例负载 | 无拓扑距离 |
| llm-d | 缓存匹配 + 负载 | 无动态拥塞 |
| Dynamo | 前缀块缓存 | 无拓扑感知 |

### 理论贡献

**命题 1（形式化）**：忽略网络项使"仅缓存感知"调度在 context length 增长时**任意次优**。

**信息不对称**：
- 推理调度器（应用层）：无物理网络拓扑/链路利用率/路由决策的可见性
- 集群运营商：有关键拓扑和遥测数据，但无 upcoming KV 传输的知识

### NetKV 解决方案

**Network Cost Oracle**：thin operator-to-scheduler interface

不需要：
- 深度集成
- 调度器理解推理语义
- 原始拓扑数据

只需要：**周期性更新的小信号**
- 实例对的 locality-tier 分类
- 每层带宽估计
- 拥塞指标

**O(|D|) 贪心算法 — NetKV**

每请求选择 decode 实例：
- 消费 oracle 输出
- Tier 排名 provably robust to stale telemetry

**网络模型**：

```
Tier 0：同节点（NVLink/PCIe，100-600 GB/s）
Tier 1：同 rack（RoCE，25-100 Gbps）
Tier 2：同 pod（单 aggregation/spine hop，10-25 Gbps）
Tier 3：跨 pod（core layer，5-12 Gbps）
```

**命题 2**：Tier 排名在拥塞遥测过时情况下有足够的鲁棒性条件。

### 关键数据

64-GPU four-tier fat-tree 模拟器（Mooncake traces 驱动）：

| 指标 | 结果 |
|------|------|
| TTFT 降低（vs round-robin）| **21.2%** |
| TTFT 降低（vs 缓存+负载感知调度器）| **17.6%** |
| SLO 达成率提升 | **20.1 百分点** |
| TBT 开销 | **<0.5 ms**（所有测试条件）|

### 特点

- 无需修改传输层 / 推理引擎 / 硬件
- 作为评分插件部署到现有调度器
