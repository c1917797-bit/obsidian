# 研究方法：技术驱动 v2.0（情报工程对接版）

> 版本: v2.0 | 更新: 2026-06-28
> 技术驱动是以「新技术/新论文」为起点，推导它能解决产品中的什么问题。
> 与业务驱动（以产品约束为起点）形成双轮驱动。
> **v2.0 新增：评分者一致性测试 + 基础/工程化分类 + 反方证据评分**

**本文件对接 AI Intelligence OS (情报工程) 现有系统，直接复用其采集、分类、评分、报告能力。**

---

## 一、核心思想

```
业务痛点驱动：产品瓶颈 → 哪个技术 → 论文验证 → 落地
技术驱动：     新技术 → 能解决什么 → 我的产品有没有这个问题 → 提前研究
```

**技术驱动的本质**：不是等出了问题再找答案，而是看到新工具后主动找它的用武之地。

## 三、v2.0 评分卡重构（核心改进）

### 3.1 综合得分公式（保留）

```
综合得分 = 技术深度(1~3) × 工程影响(1~3) × 趋势强度(1~2) × 行业影响(1~2)
```

### 3.2 v2.0 新增：反方证据评分（5 维）

```
反方证据得分 = 历史失败风险(1~3) + 专利壁垒(1~3) + 资源门槛(1~3)
              + 团队不匹配(1~3) + 反向场景(1~3)
```

**反方得分判断**：
- 0-5 分：低风险
- 6-10 分：中风险，需缓解
- 11-15 分：高风险，需备选

### 3.3 v2.0 新增：按研究类型区分权重

| 维度 | 基础研究权重 | 工程化权重 | 混合型权重 |
|------|------------|------------|-----------|
| 技术深度 | **50%** | 30% | 40% |
| 工程影响 | 30% | **50%** | 40% |
| 趋势强度 | 10% | 10% | 10% |
| 行业影响 | 10% | 10% | 10% |
| **反方证据** | **-30%** | **-20%** | **-25%** |

**反方证据作为减分项**：综合得分 = (4 维加权和) × (1 - 反方证据比例)

### 3.4 决策规则

```
if (综合得分 >= 8) {
  行动 = "立即立项，进入战略分析"
} else if (综合得分 >= 6) {
  行动 = "存入观测信号池，每周批量复盘"
} else if (综合得分 >= 4) {
  行动 = "归档，仅作为参考"
} else {
  行动 = "直接移除，不处理"
}
```

**v2.0 新增**：反方证据高的课题即使综合得分高也需重新评估

```
if (综合得分 >= 8) {
  if (反方证据得分 >= 11) {
    行动 = "高反方风险，必须有备选方案"
  } else if (反方证据得分 >= 6) {
    行动 = "中反方风险，需要风险缓解"
  } else {
    行动 = "低反方风险，立即立项"
  }
}
```

## 四、v2.0 新增：评分者一致性测试

> **v1.0 缺失**的评分验证，导致评分主观性无法量化

### 4.1 Krippendorff's alpha 测试

**方案**：
```
1. 让 3-5 个团队成员独立评分 25 个课题
2. 计算 Krippendorff's alpha 系数
3. 系数 < 0.6 表示评分一致性差，需要细化评分标准
```

**判断标准**：
- α ≥ 0.8：高度一致，方法论可信
- 0.6 ≤ α < 0.8：基本一致，需小幅调整
- 0.4 ≤ α < 0.6：一致性差，需大改
- α < 0.4：方法论不可用

### 4.2 评分卡细化（针对一致性差的部分）

**常见评分分歧点**：
- "技术深度 2 vs 3" 的边界是什么？
- "工程影响 1 vs 2" 的标准是什么？

**细化方法**：
- 每个评分维度提供 3 个具体例子
- 例：技术深度 3 = "提出全新算法" / 2 = "在现有方法上改进" / 1 = "应用已知方法"
- 例：工程影响 3 = "解决核心瓶颈" / 2 = "有改进但非核心" / 1 = "边际改进"

### 4.3 双盲评分机制

```
方案：
  1. 评分者不知道课题的"已知标签"
  2. 评分后比较一致性
  3. 一致性低的评分者重新培训
```

### 第三步：技术验证与落地路径

#### 5.3.1 验证流程（v2.0 增强）

```
Step 1：技术成熟度确认
  □ 找到最相关的1-3篇论文
  □ 确认是否有开源代码
  □ 评估代码质量（star数、更新时间、文档）
  □ v2.0 新增：是否有专利冲突？

Step 2：差距分析
  □ 论文 vs 我的产品场景有什么区别？
  □ 精度损失/性能提升在我的场景是否可接受？
  □ v2.0 新增：精度损失是否在反方证据允许范围内？

Step 3：创新点寻找
  □ 现有方法的共同缺陷是什么？
  □ 我的产品场景有没有特殊条件可以利用？
  □ 不同技术的组合能否产生新效果？

Step 4：v2.0 新增：反方证据收集
  □ 这些论文的局限是什么？
  □ 有什么已知的失败案例？
  □ 有什么被放弃的方案？为什么放弃？

Step 5：验证实验
  □ 在产品环境运行baseline
  □ 引入新技术，测试性能
  □ 记录：性能提升 / 精度损失 / 工程复杂度
  □ v2.0 新增：是否符合时间窗要求？

Step 6：落地决策
  □ 验证成功 → 制定集成计划
  □ 验证失败 → 分析原因（区分"方法论错了"vs"执行错了"）
  □ 不确定 → 设计更小范围的验证实验
  □ v2.0 新增：是否触发方法论更新？
```

## 六、v2.0 新增：基础研究 vs 工程化分类

### 6.1 分类标准

| 类型 | 特征 | 周期 | 风险 | 评价权重 |
|------|------|------|------|---------|
| **基础研究** | 新算法/新理论/新架构 | 1-2 年 | 高 | 创新性 50% |
| **工程化** | 框架集成/性能优化/生产落地 | 1-3 月 | 中 | 工程化 50% |
| **混合型** | 新算法 + 集成 | 6 月 | 中 | 平衡 |

### 6.2 评价差异

**基础研究课题**：
- 重点评价：创新性、技术深度、理论突破
- 容忍：高风险、长周期
- 不要求：立即工程落地

**工程化课题**：
- 重点评价：稳定性、集成度、生产可用
- 容忍：技术深度一般
- 不要求：理论突破

**混合型课题**：
- 平衡评价
- 既要创新又要工程

## 八、评分卡精确定义（v2.0 增强）

## 九、v2.0 新增：方法论学习闭环

### 9.1 季度复盘机制

```
每季度末：
  1. 收集所有 P0 课题的实际进展
  2. 对比预测与实际：
     - 哪些 P0-now 仍是 P0？→ 保持
     - 哪些降级？→ 调整资源
     - 哪些漏报？→ 更新方法论
  3. 计算方法论预测准确率
  4. 更新评分卡权重（如有重大变化）
  5. 更新业务约束（如有变化）
```

### 9.2 年度方法论升级

```
每年：
  1. 全年 P0 复盘
```

## 十二、总结（v2.0 增强）

**技术驱动的核心问题**：

```
不是「我的问题该用什么技术解决」
而是「这个新技术能解决我产品中的什么问题」
```

**对接情报工程后**：

1. **扫描自动化**：利用 IntelligenceFactory 每日采集38+信源
2. **分类智能化**：利用 ClassifierAgent 按 topics_registry 分类
3. **评分标准化**：利用 problem_spaces.json 的评分规则
4. **报告常态化**：利用 Daily/Weekly/Monthly 报告节奏

**v2.0 新增的关键原则**：

1. **反方证据必查**：每个课题必须有反方证据评分
2. **研究类型必标**：基础/工程化/混合 决定评价权重
3. **时间窗必标**：P0-now/Q1/Q4 等明确时间窗
4. **跨场景必考虑**：5 场景技术共享度分析
5. **评分一致性必测**：Krippendorff's alpha ≥ 0.6
6. **方法论必复盘**：每季度回测，每年升级
