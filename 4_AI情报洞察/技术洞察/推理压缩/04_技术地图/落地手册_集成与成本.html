🔗 二、技术依赖链

蓝军22挑战：技术依赖链未标注。上游变化可能导致下游失效。
AWQ INT4 量化
依赖：autoAWQ工具 → PyTorch → CUDA
权重格式依赖：需要HuggingFace格式权重 → 转AWQ格式
框架依赖：vLLM/SGLang原生支持AWQ格式
风险：低。工具链成熟。
SnapKV（KV稀疏化）
依赖：特定attention实现 → FlashAttention版本兼容
模型架构依赖：需要标准MHA/GQA（MLA不兼容！）
框架依赖：vLLM monkey-patch（非原生集成，升级vLLM可能失效）
⚠️ 关键风险：vLLM大版本升级后monkey-patch可能break
KIVI（2bit KV量化）
依赖：自定义CUDA kernel → CUDA版本
硬件依赖：需要Ampere+(sm_80+) → 旧GPU不兼容
框架依赖：需要修改vLLM的KV cache管理层 → 深度侵入
⚠️ 关键风险：每次vLLM升级都需要重新适配kernel
DeepEP（MoE通信）
依赖：DeepSeek架构 → 特定MoE routing实现
硬件依赖：H100/H800(InfiniBand) → A100/Ethernet效果差
网络依赖：RDMA → TCP网络效果降50%+
⚠️ 关键风险：仅适用于DeepSeek类MoE，Mixtral/Llama MoE不兼容
Block-GTQ（RoPE-aware KV量化）
依赖：RoPE位置编码 → 非RoPE模型(如ALiBi)不适用
计算依赖：频域分析模块 → 额外计算开销
⚠️ 关键风险：模型换位置编码方案后失效

⚡ 五、能耗影响

蓝军18挑战：缺能效维度(Joules/token)。内存↓不等于能耗↓。
技术内存计算量能耗(tokens/Joule)净效果
INT4量化↓75%↓40-50%(INT4 Tensor Core)↑30-50%✅ 能效提升
SnapKV(8x)↓87% KV↑5-10%(选择逻辑)↑20-30%✅ 能效提升
KIVI 2bit↓75% KV↑15-25%(反量化)↑0-10%⚠️ 能效提升有限
投机解码↑(草稿模型)↑50-80%(额外计算)↓10-20%(但吞吐↑)⚠️ 单token能耗↑但总吞吐↑
DeepEP-↓(通信减少)↑(取决于网络)✅ 多节点能效提升
关键洞察：INT4量化和SnapKV是能效最优的选择。KIVI虽然省内存但反量化增加的计算可能抵消能耗收益。

🔧 配套系统优化（非压缩但必须搭配）

重要：以下技术不是压缩技术（不减少数据量），但它们是压缩技术的必要配套。压缩+系统优化=最佳效果。
技术类别为什么不是压缩为什么必须搭配
PagedAttention内存管理不减少KV，只分页管理SnapKV淘汰+PagedAttn分页=高效KV管理
FlashAttention算子优化不减少数据，只优化IOKIVI量化+FlashAttn融合=低精度高效计算
连续批处理调度优化不减少数据，只优化batchINT4省的内存→连续批处理转化为更多并发
投机解码计算加速不减少数据，并行预测INT4+投机解码=成本最低+速度最快
DistServe架构优化不减少数据，分离PD分离式+KV压缩=Prefill/Decode独立优化
DeepEP通信库不压缩通信，优化传输ExpertQuant(压缩)+DeepEP(传输)=最优MoE
组合公式：压缩技术（减数据量） + 系统优化（提效率） = 生产级推理服务
标准生产栈：AWQ INT4 + PagedAttention + FlashAttention + 连续批处理 + 投机解码

🎯 七、综合决策树

第1步：预算多少？
0.5人月 → AWQ INT4 + vLLM + FlashAttn（开箱即用）
1-2人月 → + 投机解码 + SnapKV插件
3-6人月 → + KIVI/Block-GTQ深度集成
12人月+ → + DeepEP/DistServe架构改造

第2步：硬件是什么？
H100 → INT4 + FP8 + FlashAttn v3
A100 → INT4 + FlashAttn v2（无FP8）
CPU → GGUF + llama.cpp（不碰KV压缩）
多节点IB → DeepEP（否则不要碰）

第3步：场景是什么？
Agent多轮 → SnapKV必须（KV累积）
代码助手 → 不要INT4以下（代码敏感）
长上下文 → SnapKV + Block-GTQ
MoE推理 → DeepEP（否则通信瓶颈）

第4步：能接受多大风险？
低风险 → 只用原生集成(AWQ/PagedAttn/FlashAttn)
中风险 → 插件级(SnapKV/投机解码)
高风险 → 自定义kernel(KIVI/Block-GTQ)
极高风险 → 架构改造(DeepEP/DistServe)
