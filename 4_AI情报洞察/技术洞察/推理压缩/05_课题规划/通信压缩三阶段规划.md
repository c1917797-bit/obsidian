# 通信压缩三阶段技术规划

> 版本: v1.0 | 日期: 2026-06-29
> 平台: Ascend NPU（910B/910C）+ mindie + HCCL
> 目标: MoE推理通信时延↓30-50% · 通信占推理时间从40%降到<20%
> 竞品: DeepSeek+DeepEP（GPU+FP8）

---

## 总体路线图

```
Phase 1 (2026 Q3-Q4): 落地已有成果 —— FP8通信 + Expert跳过 + 同步点丢弃
     ↓ 通信↓20-30%
Phase 2 (2027 H1):    核心突破      —— INT4通信 + 联合压缩 + HCCL重叠
     ↓ 通信↓40-60%
Phase 3 (2027 H2+):   建立壁垒      —— 率失真全局最优 + 单Kernel融合
     ↓ 通信↓60-80%
```

# Phase 1：落地已有成果（2026 Q3-Q4）

> 目标：把学术界已验证但工业未部署的技术在Asceng上落地。3个课题，每个0.5-3人月。

---

## 课题 C1：HCCL FP8通信部署

**关键挑战**：DeepEP在GPU上实现了FP8 dispatch，但Ascend NPU的HCCL通信库不支持FP8。Qwen3-235B-MoE在8卡910C上All-to-All通信占推理时间38%（实测），FP8可降一半。

**技术目标**：对Qwen3-235B-A22B，8卡910C部署，All-to-All通信量↓50%，TPOT↓15-20%，精度损失<0.5%

**关键技术**：
1. HCCL All-to-All FP8传输：修改HCCL通信接口支持FP8数据类型dispatch/combine
2. Ascend Cube FP8反量化：利用Cube单元原生FP8算力，通信后直接FP8→BF16反量化
3. 通信-计算重叠：FP8 dispatch与Expert GEMM用不同stream重叠

**预期收益**：
```
通信时间：38% → ~19%（FP8减半）
TPOT：↓15-20%（通信占比减半的贡献）
精度：FP8通信已验证精度无损（DeepSeek-V3生产证明）
```

**开发量**：2人月（1人HCCL接口 + 1人mindie集成）

**参考**：DeepEP V2（GitHub 9.8k★，FP8 dispatch生产验证）· DeepSeek-V3 FP8

---

## 课题 C2：冷Expert跳过通信

**关键挑战**：Qwen3-235B有128个Expert，但Bottom-20%（25个）几乎不被激活（DeepSeek-V3实测87.5%是死权重）。这些冷Expert仍占显存且在EP部署中参与All-to-All通信路由。

**技术目标**：MoE显存↓20%，通信路由↓20%，精度损失<0.5%

**关键技术**：
1. Expert激活频率画像：运行时统计每个Expert的激活频率分布
2. 渐进式冻结→验证→删除：
   - Step1: 冻结Bottom-10%（不加载不计算不通信）
   - Step2: 验证PPL不上升
   - Step3: 物理删除路由表条目
3. 路由权重重平衡：删除后剩余Expert的路由权重重新校准

**预期收益**：
```
显存：128 Expert → 103 Expert，↓20%
通信路由：25个冷Expert不参与All-to-All
精度：冷Expert贡献<0.5%（激活频率极低）
```

**开发量**：3人月（画像系统1人 + 冻结验证1人 + 路由重平衡1人）

**参考**：Efficient Expert Pruning(ICLR'25, 评分5.2) · DiEP(NeurIPS'25, 评分4.7) · MoE-Infinity

---

## 课题 C3：同步点丢弃（TP通信优化）

**关键挑战**：Qwen3-235B的张量并行(TP)推理中，每层2次AllReduce（attention+FFN），94层=188次AllReduce/token。SPD证明其中30-40%的同步点可安全跳过。

**技术目标**：TP通信↓30%，TPOT↓10%，精度回退<1%

**关键技术**：
1. 层级同步敏感度测量：校准数据跑一遍，每层做"跳过vs不跳过"对比，计算敏感度分数
2. 阈值跳过策略：敏感度低于阈值的层标记为"可跳过AllReduce"
3. 残差连接误差吸收验证：确保跳过后误差被后续层自然修正

**预期收益**：
```
AllReduce次数：188次/token → ~130次/token（跳过~30%）
TP通信时间：↓30%
TPOT：↓10%（通信是TP的主要开销之一）
精度：<1%回退（SPD论文已验证）
```

**开发量**：2人月（敏感度测量1人 + mindie AllReduce跳过实现1人）

**参考**：SPD (arXiv:2502.20727, LLaMA2-70B验证, 延迟↓20%)

# Phase 2：核心突破（2027 H1）

> 目标：学术界刚提出、工业未验证的技术在Ascend上首次落地。3个课题。

---

## 课题 C4：INT4通信量化

**关键挑战**：FP8通信减半（C1），但INT4可再减半（通信↓75% vs BF16）。ExpertQuant(2025)证明小模型可行但671B未验证。Ascend Cube原生支持INT4是GPU不具备的优势。

**技术目标**：All-to-All通信量↓75%（vs BF16），TPOT↓25-35%，精度损失<1%

**关键技术**：
1. Expert参数INT4量化 + 动态精度切换：
   - 热Expert（高频激活）：FP8传输（精度优先）
   - 冷Expert（低频激活）：INT4传输（压缩优先）
   - 运行时按路由频率动态切换
2. INT4量化-通信-反量化流水线：与Expert GEMM计算重叠
3. Ascend Cube INT4原生执行：Cube单元直接处理INT4数据无需反量化（GPU Tensor Core不具备此能力）

**预期收益**：
```
通信量：BF16→INT4 = ↓75%（含热Expert用FP8的综合效果约↓60%）
TPOT：↓25-35%
精度：ExpertQuant验证<1%损失（需在Qwen3-235B上重验证）
```

**开发量**：6人月（INT4量化kernel 2人 + HCCL INT4通信 2人 + 动态精度切换 1人 + 验证 1人）

**参考**：ExpertQuant(2025, 首个MoE INT4) · DeepEP NVFP4实验分支 · Ascend Cube INT4文档

---

## 课题 C5：通信量化+Expert跳过联合

**关键挑战**：C2（Expert跳过）减通信次数，C4（INT4量化）减每次通信字节。联合可实现通信↓70-90%（两因子相乘），但跳过的Expert与量化传输的Expert可能冲突（路由不一致）。

**技术目标**：MoE通信量↓70-90%，计算量↓30%，精度损失<1%

**关键技术**：
1. "稀疏减次数+量化减字节"双降：
   - 先跳过冷Expert（减少通信次数）
   - 再对热Expert通信做INT4量化（减少每次通信字节）
   - 通信量 = 参与Expert数 × 每Expert字节数，两个因子同时压缩
2. 联合Jaccard路由损失：
   - L = L_routing + λ × L_jaccard
   - 确保跳过+量化后路由决策一致性
3. 稀疏×量化二维Pareto搜索

**预期收益**：
```
通信量：跳过↓20% × 量化↓75% = 联合↓80%
精度：Jaccard损失约束确保<1%
```

**开发量**：4人月（联合架构2人 + Jaccard损失1人 + Pareto搜索1人）

**参考**：FoMoE(ICLR'26, skip机制) · FlashMoE(NeurIPS'25, 单Kernel) · RDKV(率失真理论)

---

## 课题 C6：HCCL通信-计算重叠优化

**关键挑战**：Phase1的FP8/INT4通信引入了量化-通信-反量化开销。如果不重叠，Overhead可能抵消通信节省。NVLink场景（节点内）通信已经很快，量化开销占比更高。

**技术目标**：通信-计算重叠效率>80%，量化Overhead被计算完全吸收

**关键技术**：
1. 量化→通信→反量化三段流水线：
   - Stream A: 量化Batch N的Expert输入 → HCCL dispatch
   - Stream B: 同时计算Batch N-1的Expert GEMM
   - Stream C: 同时反量化Batch N-2的Expert输出
2. HCCS+Cube协同：HCCL通信用HCCS带宽，Cube计算用算力，两者物理隔离不竞争
3. 自适应重叠：监测通信/计算比例，动态调整流水线深度

**预期收益**：
```
量化Overhead：从可见→被完全隐藏
端到端TPOT：额外↓5-10%（Phase1+C4的Overhead被吸收）
```

**开发量**：4人月（流水线设计2人 + HCCL stream管理1人 + 性能调优1人）

**参考**：DeepSeek DualPipe（生产验证）· FlashMoE(NeurIPS'25, 9x GPU利用率) · FoldMoE(ACL'25)

---

**Phase 2 小结**：
```
3个课题总开发量：14人月
总通信↓：40-60%（INT4 + 联合 + 重叠）
总TPOT↓：40-50%
精度损失：<1%

```

# Phase 3：建立壁垒（2027 H2+）

> 目标：竞品无法复制的技术壁垒。2个课题。

---

## 课题 C7：率失真全局最优通信比特分配

**关键挑战**：C4/C5的"热Expert FP8/冷Expert INT4"是人工规则。RDKV(ETH 2026)证明了用率失真理论可全局最优分配每个Expert的传输bit数（0/2/4/8/16bit），但尚未扩展到通信场景。

**技术目标**：通信量↓60-80%（vs BF16），全局最优比特分配，精度损失<1%

**关键技术**：
1. 通信率失真模型：
   - 每个Expert的"通信率"= 传输bit数
   - 每个Expert的"失真"= 量化后输出与原始输出的KL散度
   - 目标：min Σ失真，s.t. Σ通信率 ≤ 预算
2. 注水算法求解：
   - 冷Expert（低失真敏感度）→ 分配0bit（不传）= 淘汰
   - 温Expert（中敏感度）→ 分配2-4bit（INT2/INT4）
   - 热Expert（高敏感度）→ 分配8bit（FP8）
   - 全局最优，不是人工规则
3. 在线自适应：随请求类型变化动态更新敏感度画像

**预期收益**：
```
通信量：全局最优分配 vs 人工规则 → 额外↓10-20%
精度：率失真最优保证（理论最优Pareto前沿）
```

**开发量**：8人月（率失真模型3人 + 注水算法3人 + 在线自适应2人）

**参考**：RDKV(arXiv:2605.08317, ETH Zürich, 率失真统一) · 信息论注水算法

---

## 课题 C8：单Kernel融合量化+通信+计算

**关键挑战**：Phase2的量化/通信/计算是三个独立操作。FlashMoE证明单Kernel融合可获9x GPU利用率，但FlashMoE没做量化。融合量化+通信+计算的单Kernel在NPU上无人尝试。

**技术目标**：通信-计算重叠效率>95%，量化Overhead=0（完全融入Kernel）

**关键技术**：
1. Ascend单Kernel融合设计：
   ```
   Kernel内部流水线：
   Block 0: INT4量化(token输入) → HCCL dispatch(INT4)
   Block 1: Expert GEMM(上一个token) ← Cube计算
   Block 2: HCCL combine → INT4反量化
   → 细粒度重叠，零launch开销
   ```
2. Cube+HCCS物理隔离利用：
   - Cube单元做GEMM计算
   - HCCS做通信
   - 两者物理隔离不竞争资源 → 天然可重叠
3. Ascend特有优势：
   - Cube单元原生INT4 → 量化/反量化零开销
   - GPU Tensor Core不支持INT4原生 → 这是NPU独有壁垒

**预期收益**：
```
GPU利用率：>95%（FlashMoE在GPU上是9x提升，NPU Cube+HCCS隔离更好）
量化Overhead：0（完全融入Kernel）
端到端TPOT：额外↓10-15%
```

**开发量**：10人月（Kernel设计4人 + Ascend C++实现4人 + 性能调优2人）

**参考**：FlashMoE(NeurIPS'25, 单Kernel 9x) · DeepEP V2(JIT编译) · Ascend Cube架构文档

---

```
2个课题总开发量：18人月
```

## NPU独有优势（竞品无法复制）

```
1. Ascend Cube单元原生INT4/INT2 → 量化/反量化零开销
   GPU Tensor Core不支持INT4原生 → 必须反量化

```
