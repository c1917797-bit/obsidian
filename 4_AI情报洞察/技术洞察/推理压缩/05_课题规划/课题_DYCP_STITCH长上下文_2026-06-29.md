# 课题：面向通话翻译的动态分块+分块拼接长上下文压缩根技术

> 核心方法：DYCP（Dynamic Chunking）+ STITCH（Chunked Reasoning Stitching）
> 场景：通话助手多轮长对话 + 智能翻译长文本
> 硬件：Ascend NPU 910B/910C

---

## 一、方法来源

### DYCP（Dynamic Chunking）— 动态分块

来源论文：
- [ICLR 2026] Dynamic Chunking for End-to-End Hierarchical Sequence Modeling
  核心：不是固定大小分块，而是根据内容语义动态确定块边界
  创新：学习一个分块器，自动在语义边界处切分

- [ACL 2025] Dynamic Chunking and Selection for Reading Comprehension of Ultra-Long Context
  核心：动态分块 + 块级选择（只读重要块）
  创新：不是所有块都值得全量处理

### STITCH — 分块推理拼接

来源论文：
- [ICLR 2026] STITCH: Simultaneous Thinking and Talking with Chunked Reasoning for Spoken Language Models
  核心：语音模型中"边想边说"，将推理过程分成块
  创新：chunked reasoning → 块间拼接 → 无缝输出

- [ACL 2025] StitchLLM: Serving LLMs, One Block at a Time
  核心：分块服务LLM，按块加载/卸载
  创新：块级KV管理，降低峰值显存

## 二、核心问题

```
128K长上下文的三个矛盾：

矛盾1：全局注意力 vs 计算量
  全局注意力O(n²)：128K×128K = 16B次运算
  但实际99%的attention score接近0（远距离几乎不相关）
  → 需要动态分块，只在块内全注意力

矛盾2：KV完整性 vs 内存
  完整KV：128K × 32层 × 128头 × 128维 × 2(K,V) = ~4GB/层
  但大部分历史KV不再被关注
  → 需要块级KV压缩+拼接

矛盾3：翻译/通话的局部性 vs 全局一致性
  翻译：句子间有依赖但弱（术语一致性）
  通话：轮次间有依赖但弱（上下文记忆）
  → 需要块内全注意力 + 块间稀疏桥接
```

## 三、技术方案：DYCP-STITCH

### 总体架构

```
128K长上下文输入
    │
    ▼
┌─────────────────────────────┐
│ DYCP模块：动态语义分块        │
│                             │
│ 输入：128K token序列          │
│ 轻量分块器（MLP，<10M参数）   │
│ 输出：N个语义块               │
│   块1: [token 1-3K] 对话开头 │
│   块2: [token 3K-8K] 主题A   │
│   块3: [token 8K-15K] 主题B  │
│   ...                        │
│   块N: [token 120K-128K] 最近│
│                             │
│ 关键：块大小不固定，按语义边界 │
│ 通话：按对话轮次边界          │
│ 翻译：按句子/段落边界         │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│ 块内处理（独立全注意力）       │
│                             │
│ 每个块内部：标准全注意力       │
│ 块大小3K-15K → 计算量可控     │
│ 块内KV：INT4量化（Cube原生）  │
│                             │
│ 块1: 3K tokens → O(3K²) ≈ 9M│
│ 块2: 5K tokens → O(5K²) ≈ 25M│
│ ...                        │
│ 总计：≈ O(sum(chunk_i²))     │
│ vs 全局：O(128K²) = O(16B)  │
│ → 计算量降低100-1000×        │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│ STITCH模块：块间拼接          │
│                             │
│ 问题：块间如何传递信息？       │
│                             │
│ 方案A：Sink Token桥接         │
│   每个块保留前2个token作为sink│
│   下一块通过sink访问上一块     │
│   类似StreamingLLM的跨块版    │
│                             │
│ 方案B：摘要Token拼接           │
│   每个块结束后生成1个摘要token │
│   摘要token的KV作为桥接       │
│   类似STITCH的chunked reasoning│
│                             │
│ 方案C：检索式桥接              │
│   当前块通过检索访问历史块KV   │
│   只检索相关的块，不全部连接   │
│   类似RAG但检索的是KV而非文本 │
│                             │
│ 我们的选择：方案B+C混合        │
│   相邻块：摘要Token桥接（STITCH）│
│   远距离块：检索桥接（检索式）  │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│ 输出生成                     │
│                             │
│ 当前块的KV + 桥接KV          │
│ → LLM生成（Cube INT4执行）   │
│ → 流式输出（边翻边说）       │
└─────────────────────────────┘
```

### 三个核心模块详解

#### 模块1：DYCP动态分块器

```
目标：将128K输入动态切成语义连贯的块

方法：
  ① 边界检测器（轻量MLP）
     输入：每个token的hidden state
     输出：该token是否为块边界（二分类）
     训练：在通话/翻译数据上学习语义边界

  ② 通话场景的分块策略
     对话轮次边界 → 块边界
     "用户:..." → "助手:..." 是一个块
     闲聊轮次合并为一个小块
     重要问答各自独立成块

  ③ 翻译场景的分块策略
     段落边界 → 块边界
     长段落按句子二次分块
     术语密集区 → 更大块（保留上下文）
     简单区 → 更小块（省算力）

  NPU适配：
    分块器MLP用INT8在Cube上运行
    分块结果指导KV Cache的分块存储
```

#### 模块2：块内INT4压缩注意力

```
目标：每个块内部用INT4做全注意力

方法：
  每个块（3K-15K token）：
    KV Cache INT4量化（课题Q3的渐进量化）
    注意力计算用Cube INT4指令
    块内计算量：O(chunk_size²) 而非 O(128K²)

  示例：
    128K分成10个块（平均12.8K/块）
    块内计算：10 × O(12.8K²) = 1.6B
    vs 全局：O(128K²) = 16B
    → 计算量降低10×

  NPU优势：
    每个块映射到一组Cube单元
    块间通过HCCL通信传递桥接Token
```

#### 模块3：STITCH块间拼接

```
目标：块之间信息传递，保证全局一致性

三种桥接策略（按距离分层）：

┌──────────────────────────────────────┐
│ 相邻块（距离=1）                     │
│ 摘要Token桥接（来自STITCH思想）      │
│                                      │
│ 块i结束后 → 生成1个摘要Token         │
│ 摘要Token的KV → 注入块i+1的KV Cache │
│ 块i+1能看到块i的"要点"               │
│                                      │
│ 类比：人脑记住上一段对话的"要点"      │
├──────────────────────────────────────┤
│ 近距离块（距离=2-5）                  │
│ 多摘要Token拼接                       │
│                                      │
│ 保留最近5个块的摘要Token              │
│ 形成紧凑的"短期记忆"                  │
│                                      │
│ 类比：人脑的工作记忆                  │
├──────────────────────────────────────┤
│ 远距离块（距离>5）                    │
│ 检索式桥接                           │
│                                      │
│ 当前块的query → 检索历史块的KV        │
│ 只检索相关的块（attention score > θ） │
│ 非相关块不访问                       │
│                                      │
│ 类比：人脑的"回忆"机制               │
└──────────────────────────────────────┘
```

## 四、与通话翻译场景的对齐

### 通话助手场景

```
50轮通话 + 128K历史

DYCP分块：
  第1-5轮（寒暄）：合并为1个小块（1K token）
  第6-15轮（主题A讨论）：1个块（15K token）
  第16-25轮（主题B讨论）：1个块（15K token）
  ...
  第46-50轮（当前对话）：1个块（8K token）

STITCH拼接：
  当前块（第50轮）需要：
    → 相邻桥接：第49轮的摘要Token
    → 近距离桥接：第46-49轮的摘要Token
    → 检索桥接：第8轮用户提到的关键信息（检索命中）

效果：
  当前推理只加载：8K当前块 + 5个摘要Token + 检索到的少量历史KV
  vs 全量加载128K KV → 内存降低10-50×
```

### 智能翻译场景

```
128K长文本翻译

DYCP分块：
  按段落分块：
    块1：第1-3段（引言，8K token）
    块2：第4-7段（方法，20K token）→ 术语密集，更大块
    块3：第8-10段（实验，15K token）
    ...
    当前块：正在翻译的段落（5K token）

STITCH拼接：
  当前翻译段落需要：
    → 相邻桥接：上一段的摘要Token（段落衔接）
    → 检索桥接：全文中的术语定义（检索"该术语首次出现的位置"）
    → 检索桥接：全文中的人名/地名一致性

效果：
  翻译时注意力计算只覆盖当前段落 + 检索结果
  vs 128K全局注意力 → 计算量降低20-100×
  术语一致性通过检索桥接保证
```

|------|--------|-------------|---------|-------------------|----------------|

## 六、NPU优势

```
Ascend 910B/910C的独特价值：

① 块级Cube映射
   每个块 → 一组Cube单元
   块内INT4注意力 → Cube原生INT4
   块间摘要Token传递 → HCCL通信

② 流式处理
   通话/翻译是流式的（边输入边处理）
   NPU可以pipeline：块i处理时，块i+1在加载
   GPU做不到INT4原生 → NPU是唯一能高效执行的平台

③ 端侧部署
   910B 64GB → 当前块(8K) INT4 KV ≈ 0.1GB
   桥接Token(50个) INT4 KV ≈ 0.001GB
   总显存占用 < 1GB → 端侧可部署
```

## 九、创新点总结

```
创新1：语义驱动动态分块（DYCP到通话/翻译）
  不是固定大小切分，而是按对话轮次/段落语义切分
  通话：轮次边界 + 行为类型感知
  翻译：段落边界 + 术语密度感知

创新2：三层距离感知桥接（STITCH扩展）
  相邻块：摘要Token（STITCH思想）
  近距离：多摘要短期记忆
  远距离：检索式访问（RAG-on-KV思想）
  按距离分层是新的设计

创新3：NPU Cube块级映射
  每个块映射到独立Cube单元组
  INT4块内注意力 + HCCL块间通信
  这是NPU独有的执行模型
```
