# 研究方法：业务驱动 v2.0

> 版本: v2.0 | 更新: 2026-06-28
> 业务驱动是以「产品约束」为起点，推导需要研究的技术方向。
> 与技术驱动（以新技术/新论文为起点）形成双轮驱动。
> **v2.0 新增：反方约束 + 跨场景映射 + 5 场景适配**

---

## 一、核心思想

```
❌ 论文驱动研究（别人做什么我做什么）
✅ 约束驱动研究（我的产品需要什么）
✅ 空白格驱动创新（在没人做的地方你就是先行者）
```

**业务驱动的本质**：不是等论文告诉你做什么，而是从产品约束出发，找到必须解决的核心问题，再从论文里找验证和启发。

## 二、业务约束模型（第一步）

**不动论文，先回答六个问题**。这六个问题的答案决定了你应该研究什么、不应该研究什么。

### 2.1 5 场景业务约束六问

---

#### 场景 A：LLM 文本推理

```
Q1: 我的产品是单卡推理还是多卡推理？
    → 答案：多卡推理（MoE 架构）
    → 结论：通信压缩是必选项，不是可选项

Q2: 我的产品主要处理的序列长度分布是什么？
    → 答案：128K~1M 长上下文
    → 结论：KV Cache 是主要显存消费者，KV 压缩是核心

Q3: 我的产品的延迟要求是多少？
    → 答案：TPOT 领先 30%（时延降低 30%）
    → 结论：必须解决 KV 访存瓶颈（TPOT 的主要来源）

Q4: 我的产品支持的最大并发是多少？
    → 答案：高并发（Agent 多轮场景，数十至数百路）
    → 结论：显存容量是硬约束，KV Cache 压缩直接决定并发上限

Q5: 我的产品对精度的容忍度是多少？
    → 答案：≤1% 精度损失
    → 结论：INT4 是上线（2-bit 需要验证）

Q6: 我的产品是什么类型的模型？
    → 答案：MoE 架构（DeepSeek-V3/Kimi K2/Qwen3-Max）
    → 结论：通信压缩 + 参数压缩协同，但通信是新增瓶颈
```

#### 场景 B：Agent 多轮

```
Q1: 多轮轮数？
    → 平均 10-50 轮，复杂任务 100+ 轮
Q2: 工具调用频次？
    → 平均每轮 0.5-2 次工具调用
Q3: 状态保存时长？
    → 长时任务：小时级；持续对话：天级
Q4: 多 Agent 协同？
    → 偶尔需要（5-10% 场景）
Q5: Function Call 标准化？
    → MCP/A2A 协议逐渐普及
Q6: 持久化记忆需求？
    → 是，Agent 核心需求
```

#### 场景 C：多模态

```
Q1: 模态类型？
    → 图像+视频+音频+文本 多模态混合
Q2: 输入模态数量？
    → 1-3 模态（VLM 是主流，视频开始爆发）
Q3: 实时 vs 离线？
    → 70% 实时（视频流/直播），30% 离线（图分析）
Q4: 分辨率要求？
    → 图像：1024×1024 起步；视频：720p 主流，4K 增长
Q5: 多模态融合时机？
    → 早期融合（图像 token 直接进 LLM）
Q6: 输出模态？
    → 文本为主，少数输出图像/视频
```

#### 场景 D：ASR 语音识别

```
Q1: 实时 vs 离线？
    → 80% 实时（会议/直播/客服）
Q2: 流式窗口大小？
    → 0.5-1.5 秒（流式延迟容忍度）
Q3: 支持语种数？
    → 中英为主（80%），多语种 20%
Q4: 噪声环境？
    → 真实场景噪声是主要挑战
Q5: 长音频处理？
    → 1 小时会议音频是常见场景
Q6: 说话人分离？
    → 60% 场景需要（多人会议）
```

#### 场景 E：TTS 语音合成

```
Q1: 实时合成延迟？
    → First Audio <300ms（流式）
Q2: 多说话人需求？
    → 70% 场景（数字人/有声书）
Q3: 情感/韵律需求？
    → 数字人必备，传统 TTS 一般
Q4: 跨语言？
    → 多语种 TTS 是趋势
Q5: 长文本稳定性？
    → 章节级文本需要韵律一致性
Q6: 音质要求（MOS）？
    → MOS >4.0（接近真人）
```

### 2.2 约束过滤表（从六个问题推导）

| 压缩对象 | 是否必要 | 理由 |
|---------|---------|------|
| KV Cache 压缩 | ✅ 必要 | 长上下文 + 高并发，显存瓶颈 |
| 通信压缩 | ✅ 必要 | MoE 多卡，通信占比 40-60% |
| 参数压缩 | ⚠️ 参考 | 已有基础（INT4 是标配），不是主要瓶颈 |
| 推测解码 | ⚠️ 可选 | 可提升时延，但优先级低于上述两者 |

## 三、What × How 矩阵（第二步）

### 3.1 构建研究空间矩阵

压缩技术有两个维度：

```
维度一：压缩对象（What）
  → 参数（Weight）：模型权重
  → KV Cache：推理过程中的 Key-Value 缓存
  → 激活值：中间层计算结果
  → 通信：多卡之间的数据传输
  → M 模态编码器：视觉/音频编码器
  → V 声码器：音频合成解码器
  → S 推理状态：投机解码草稿等

维度二：压缩技术（How）
  → 量化（Quantization）：精度压缩（FP16 → INT8/INT4）
  → 剪枝（Pruning）：结构化移除不重要的部分
  → 稀疏化（Sparsification）：动态稀疏激活
  → 低秩分解（Low-rank）：矩阵分解压缩
  → 蒸馏（Distillation）：知识迁移训练小模型
  → 通用优化：不归类于上述的效率优化
```

### 3.2 矩阵分析判断标准

```
论文数 = 0 的格子      →  【第一优先级】几乎确定是研究空白
论文数 1~5 的格子     →  【第二优先级】研究空白但可能有原因
论文数 6~20 的格子    →  【正常】有研究空间但也有竞争
论文数 > 50 的格子    →  【红海】除非你有独特角度否则别碰
```

### 3.3 当前研究空间矩阵（基于 3876 篇论文分析）

```
                 量化      剪枝     稀疏化    蒸馏     低秩     通用优化
             ┌────────────────────────────────────────────────────────┐
KV Cache     │   46      37       69       10      37       148      │
             │   ★★☆     ★★☆      ★★★      ★☆☆      ★★☆      ★★★★   │
权重(Weight) │  376     509      311      231     575       175      │
             │   ★★★     ★★★★     ★★★      ★★★      ★★★★★     ★★★   │
激活值       │  201     199      396       68     174        42      │

图例：
  ★★★★★ = 必做（空白格 + 产品强需求）
```

## 四、三问过滤（第三步）

空白格不等于「值得做」。对每个候选格子，回答三个问题：

```
问题A：这个方向有没有第一性原理上的必要性？
       → 多卡推理场景下，这个压缩方向是否是唯一解？
       → 如果有其他解（如更贵的硬件），压缩就不是必选

问题B：这个方向的工程实现难度有多大？
       → 需要改动分布式框架吗？
       → 需要硬件厂商配合吗？
       → 如果难度太大，三年内都无法落地

问题C：这个方向有没有潜在的负面效应？
       → 精度损失是否能被下游任务接受（≤1%）？
       → 会不会引入新的问题（如延迟不稳定）？
```

**三个问题都通过 → 进入候选。**

## 五、v2.0 新增：反方约束检查（第四步）

> **v1.0 缺失**的反方约束检查，导致方法论"自我实现预言"

**业务约束的反方检查**：

```
Q1': 我的产品约束是不是真的？
     → 客户访谈 3 家以上验证
     → 数据分析支撑（不是直觉）

Q2': 我的产品约束是不是过时的？
     → 3 个月前 vs 现在的市场需求变化
     → 技术演进（硬件/模型/场景）可能让约束失效

Q3': 我的产品约束是不是过严的？
     → 是不是把"理想状态"当作"必需要求"
     → 适当的灵活性可能带来更大收益

Q4': 我的产品约束是不是过宽的？
     → 是不是把"硬约束"当作"软约束"
     → 过度灵活导致方向不聚焦

Q5': 如果约束完全相反，会怎样？
     → 反向场景：单卡 vs 多卡、短文本 vs 长文本
     → 反向业务：端侧 vs 云端、创意 vs 推理
```

**反方约束的实际应用**：

```
案例：我的业务约束 = "多卡 MoE"
反方检查：
  Q1'：客户访谈验证：3 家客户都明确表示需要多卡
  Q2'：3 个月前 vs 现在：硬件代际更新（H200/B200）让单卡可装下更多模型
  Q3'：是不是过严？：实际有些客户用单卡也能满足需求
  Q4'：是不是过宽？：硬件限制确实存在
  Q5'：反向场景：端侧 AI 兴起，单卡可能更重要

结论：业务约束"多卡 MoE"是真实的，但需要保留 10% 资源给"单卡端侧"
```

## 七、课题命题推导（第六步）

空白格只是「研究方向」，不是「研究课题」。从方向到课题，需要具体化：

```
步骤 1：明确压缩对象和技术组合
  → 例如：KV Cache × 量化

步骤 2：回答第一性原理问题
  → KV 量化为什么是必要的？（显存不够，并发受限）
  → 现有的 KV 量化有什么问题？（2-bit 精度崩塌）

步骤 3：定义课题命题
  → 不是「做 KV 量化研究」
  → 而是「在 Agent 多轮场景下，实现 Layer-wise 自适应 2-bit KV 量化，
    精度损失 < 2%，TPOT 降低 30%」

步骤 4：拆解创新点
  → 创新点 1：层间重要性感知分配 bit（现有方法是 global 分配）
  → 创新点 2：针对 Agent 场景的特殊处理（多轮 vs 单轮不同）
  → 创新点 3：和推测解码的协同机制

步骤 5：v2.0 新增：反方证据
  → 历史失败案例：过去 3 年类似方向为什么失败？
  → 专利风险：是否被 DeepSeek/Google 等专利保护？
  → 备选方案：备选方案 1/2/3

步骤 6：v2.0 新增：跨场景复用
  → 这个课题能复用到其他场景吗？
  → 复用的收益有多大？
```

## 八、论文验证（第七步）

这是唯一需要大量读论文的环节。但目的变了：

```
之前：别人做什么我做什么（被动跟随）
现在：这个课题的技术路径有哪些已知方案？局限在哪里？我的创新点在哪里？
```

**验证流程**：

```
Step 1：找到这个方向的核心论文（3-5 篇）
  → 引用最高的几篇（理解技术成熟度）
  → 最新论文（理解前沿进展）

Step 2：分析每个论文的技术路径和局限性
  → 这个方法为什么还没解决你的问题？
  → 精度损失来源是什么？
  → 工程落地的障碍是什么？

Step 3：找到创新点
  → 现有方法的共同缺陷是什么？
  → 你的产品场景有没有别人没有的特殊条件？
  → 不同技术的组合能否产生新的效果？

Step 4：v2.0 新增：反方证据收集
  → 这些论文的局限是什么？
  → 有什么已知的失败案例？
  → 有什么被放弃的方案？为什么放弃？

Step 5：设计验证实验
  → 在你的产品环境测试（不是只跑 benchmark）
  → 真实 workload 的性能 vs 精度 trade-off
```

## 十、与技术驱动的协同

```
业务驱动：解决现在的问题（紧迫）
  → 从产品约束出发
  → 找能解决当前瓶颈的技术

技术驱动：储备未来的问题（重要）
  → 从新技术出发
  → 找能用在产品中的场景

v2.0 新增：双轮驱动的反方协同
  → 业务驱动找到的方向，需要技术驱动验证（反方证据）
  → 技术驱动找到的方向，需要业务驱动评估（市场需求）
```
