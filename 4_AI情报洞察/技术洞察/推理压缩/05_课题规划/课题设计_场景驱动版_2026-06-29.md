# 推理压缩课题设计（场景驱动版）

> 模型：LLM/VLM
> 数据：长上下文
> 硬件：Ascend NPU 910B/910C（Cube原生INT2/INT4）
> 场景：通话助手（实时多轮）+ 智能翻译（长文本低延迟）
> 设计原则：每个课题必须解决场景中的真实痛点，而非通用压缩

---

# 一、量化（3个课题）

---

## 课题Q1：通话历史时间衰减渐进KV量化

### 场景痛点
通话助手50轮对话 → KV Cache累积达数百GB。但对话信息有明显的时间衰减性：最近3轮的KV是当前对话核心（必须高精度），30轮前的闲聊几乎不再被引用（可以极低精度）。

### 核心创新
**按对话轮次的时间衰减分配bit-width**：
```
最近1-3轮：  INT8（当前对话，高精度，占10% KV）
4-15轮：    INT4（近期上下文，中精度，占30% KV）
16-50轮：   INT2（历史记忆，低精度，占60% KV）

总均bit-width ≈ 2.5-bit（vs 统一INT8的8-bit → 3.2×压缩）
```

与现有方法的区别：
- KVTuner按"层"差异化 → 我们按"对话轮次"差异化
- ThinKV按"Thought类型"差异化 → 我们按"时间衰减"差异化
- KIVI统一2-bit → 我们渐进2/4/8-bit

### NPU优势
Ascend Cube同时支持INT2/INT4/INT8三档运算。一轮对话的KV根据时间标签路由到不同精度Cube指令——GPU无法做到INT2原生运算。

### 参考技术
- KVTuner [ICML 2025] — 层感知混合精度KV量化（我们的"轮次感知"是对标升级）
- KIVI [ICML 2024] — K per-channel + V per-token 2-bit（INT2基础）
- OSCAR [2026] — Attention感知谱旋转INT2（远期轮次的安全INT2）
- ThinKV [ICLR 2026 Oral] — Thought类型差异化bit（方法论参考）
- PM-KVQ [ICLR 2026] — 渐进混合精度KV（渐进思路参考）

### 技术目标
50轮通话场景：KV总均2.5-bit，最近3轮INT8零损失，通话质量BLEU/ROUGE损失≤2%

## 课题Q2：双语翻译源/目标KV差异化量化

### 场景痛点
智能翻译时KV Cache中有两种语言的KV：源语言（输入文本）和目标语言（已生成翻译）。源语言KV是"翻译参考"——翻译完一句后其重要性急剧下降；目标语言KV是"生成依据"——需要保持高精度保证翻译连贯性。

### 核心创新
**按语言角色分配bit-width**：
```
源语言KV：INT4（翻译参考，允许精度损失）
目标语言KV：INT8（生成依据，高精度保持）
切换点：句子级翻译完成后，该句的源语言KV从INT8降级为INT4
```

验证假设：翻译attention分数在句子翻译完成后对源语言的关注急剧衰减——可用attention map验证。

### 参考技术
- KIVI [ICML 2024] — K/V非对称（我们的"源/目标非对称"是对标升级）
- Block-GTQ [2026] — RoPE频域感知（长文本翻译的频域差异）
- KVQuant [ICML 2024] — Pre-RoPE消除异常值（源语言KV的异常值处理）

### 技术目标
128K token翻译场景：源语言KV INT4 + 目标语言KV INT8，翻译BLEU损失≤1%，KV总压缩3-4×

## 课题Q3：NPU Cube原生INT2免反量化注意力算子

### 场景痛点
当前INT2 KV量化的推理流程：INT2存储→反量化为FP16→FP16注意力计算→输出。反量化开销抵消了存储节省。Ascend Cube支持INT2原生运算但无人利用。

### 核心创新
**设计Cube INT2原生注意力kernel**：
```
当前：INT2 KV → 反量化FP16 → FlashAttention → 结果
我们：INT2 KV → Cube INT2点积 → INT2注意力 → 结果

关键：利用Cube的INT2乘加指令直接计算Q×K^T
不需要反量化，端到端INT2注意力
```

### NPU优势
这是NPU独有的——GPU没有INT2原生tensor core。Ascend Cube的INT2指令是华为硬件壁垒。

### 参考技术
- SageAttention [ICLR 2025] — 8-bit注意力（我们的INT2是对标升级）
- FlashAttention [NeurIPS 2022] — IO-aware注意力（kernel设计参考）
- KIVI [ICML 2024] — 2-bit KV量化（INT2 KV的数据基础）
- OSCAR [2026] — INT2安全旋转（INT2 KV的精度保证）

### 技术目标
LLM注意力计算：INT2 Q×K全程无反量化，注意力延迟降低2-3×（vs INT2存储+FP16计算）

# 二、稀疏（3个课题）

---

## 课题S1：通话行为感知的KV语义稀疏

### 场景痛点
通话助手中不同对话行为的KV价值差异巨大：
- 用户提问+助手回答：KV高价值（需全量保留）
- 闲聊寒暄（"你好""谢谢"）：KV低价值（可稀疏化）
- 系统指令（"请翻译以下内容"）：KV关键（必须保留）
- 错误重试/打断：KV可丢弃（无效对话）

现有方法（SnapKV/H2O）对所有内容统一评分，不区分对话行为。

### 核心创新
**对话行为分类器驱动的差异化KV保留**：
```
轻量分类器（MLP，<1M参数）预测每个对话轮次的行为类型：
  - Question/Answer → 全量KV保留
  - Chitchat → 仅保留最近1轮
  - Command → 全量 + 优先级标记
  - Translation → 滑动窗口保留
  - Error/Retry → 标记为可丢弃

稀疏策略按行为类型差异化执行
```

### 参考技术
- SnapKV [NeurIPS 2024] — 观察窗口投票（行为感知的前置基础）
- DuoAttention [ICLR 2025] — 检索头vs流式头（对话中的关键信息保护）
- KVzip [2025] — Query无关驱逐（闲聊轮次的自动淘汰）
- LazyLLM [ICLR 2025] — 可恢复稀疏（打断后恢复上下文）

### 技术目标
50轮通话：行为感知保留20% KV，通话任务成功率≥95%（vs全量KV的97%）

---

## 课题S2：流式翻译滑动窗口注意力稀疏

### 场景痛点
翻译128K长文本时注意力天然集中在"当前翻译位置"附近——正在翻译的句子需要精确attention到源文本对应位置，但100K外的文本几乎不被关注。现有方法对全部128K统一压缩。

### 核心创新
**翻译位置驱动的滑动窗口稀疏**：
```
当前翻译句子±2句：  全注意力（高精度翻译区）
当前段落其他句子：   稀疏注意力（保留实体/术语KV）
其他段落：          仅保留首尾sink token + 段落摘要KV

窗口自适应：
  简单句子（短句/常见词）：窗口缩小（省算力）
  复杂句子（长句/专业术语）：窗口扩大（保精度）
```

### 参考技术
- StreamingLLM [ICLR 2024] — Sink + Window（窗口稀疏基础）
- SnapKV [NeurIPS 2024] — 观察窗口聚类选择
- LongGen [ICLR 2025] — 1/3全注意力 + 2/3高效层（混合架构参考）
- TidalDecode [ICLR 2025] — 位置持久稀疏注意力

### 技术目标
128K翻译场景：注意力计算量降低5-10×，BLEU损失≤0.5

## 课题S3：多模态通话中的跨模态KV差异化稀疏

### 场景痛点
通话中如果包含视觉输入（屏幕共享/图片/视频通话画面），VLM同时缓存文本KV和视觉KV。视觉KV远大于文本KV（一张图2570 token），但大部分视觉信息在通话进行后不再被关注。

### 核心创新
**跨模态对齐分数驱动的KV稀疏**：
```
文本query与视觉patch的attention分数 = 跨模态对齐分数
  高对齐patch（用户正在询问的内容）：全量KV保留
  低对齐patch（无关背景）：KV稀疏化/丢弃
  随通话推进动态更新对齐分数
```

### 参考技术
- VoCo-LLaMA [CVPR 2025] — 视觉Token压缩576×
- VL-Cache [ICLR 2025] — VLM KV 90%↓
- KVCapsule [2026] — VLM非对称冗余2×TPS
- SparseVLM [2025] — 视觉Token动态稀疏

### 技术目标
5图通话场景：视觉KV压缩8×，VQA准确率损失≤2%

# 三、蒸馏（3个课题）

---

## 课题D1：通话记忆蒸馏——历史KV压缩为记忆Token

### 场景痛点
50轮通话历史的KV Cache即使量化+稀疏后仍然巨大。人类不会记住对话的每个字——只记住"要点"。能否训练一个"记忆编码器"将历史KV压缩为固定数量的"记忆Token"？

### 核心创新
**通话记忆编码器**：
```
输入：最近N轮的全部KV Cache（经过稀疏+量化后的）
记忆编码器：轻量Transformer（4层，<50M参数）
输出：固定64个"记忆Token"的KV

下一轮生成时：
  当前用户输入的KV + 64个记忆Token KV → LLM生成

类比：
  人脑"工作记忆"只保留最近几轮对话
  "长期记忆"压缩为要点
  我们的64个记忆Token = 长期记忆的压缩表示
```

### 学术空白
数据库验证：Decoding阶段KV蒸馏 = 0篇。这是最大的研究空白。

### 参考技术
- KVSculpt [2026] — 连续空间KV优化（L-BFGS+闭式解，理论基础）
- Activation Beacon [ICLR 2025] — 激活直接压缩+随机压缩比训练
- KV-Distill [2025] — Question-independent 99%长度缩减
- SwiftKV [2024] — Prefill阶段KV蒸馏（我们做Decoding阶段）

### 技术目标
50轮通话：历史KV压缩为64个记忆Token（压缩比>100×），通话质量损失≤3%

---

## 课题D2：翻译质量驱动的KV蒸馏

### 场景痛点
通用KV蒸馏用KL散度对齐注意力分布，但翻译任务的质量指标是BLEU/COMET——分布接近不等于翻译质量好。需要翻译质量感知的蒸馏。

### 核心创新
**翻译质量多目标蒸馏损失**：
```
L = α·L_KL(注意力分布对齐)
  + β·L_BLEU(翻译质量保持)
  + γ·L_COMET(语义保持)
  + δ·L_term(术语一致性)

蒸馏优化方向：压缩KV时优先保留对翻译质量贡献大的信息
不同语言对（中英/中日/中阿）的KV重要性分布不同
```

### 学术空白
翻译质量感知KV蒸馏 = 0篇

### 参考技术
- KVSculpt [2026] — KL优化KV蒸馏（质量感知是对标升级）
- SwiftKV [2024] — Prefill蒸馏方法论
- Activation Beacon [ICLR 2025] — 随机压缩比训练（多目标训练参考）
- Divide-or-Conquer [EMNLP 2024] — LLM推理蒸馏（分阶段蒸馏参考）

### 技术目标
128K翻译场景：KV蒸馏压缩8×，BLEU损失≤0.5，COMET损失≤1分

---

## 课题D3：通话管线ASR-LLM-TTS跨段联合蒸馏

### 场景痛点
通话管线三段独立：ASR（编码器624M）→LLM（7B）→TTS（声码器24M）。每段各自缓存KV，跨段传输有冗余。当前延迟>1秒，无法实时。

### 核心创新
**跨段中间表示蒸馏**：
```
ASR→LLM：ASR编码器输出直接蒸馏为LLM可用的embedding
  （跳过ASR解码器→文本→LLM tokenizer→LLM embedding的冗余链路）

LLM→TTS：LLM输出直接蒸馏为TTS声码器输入
  （跳过LLM文本→TTS tokenizer→TTS embedding的冗余链路）

联合优化：三段的KV Cache联合压缩
  ASR的声学KV + LLM的语言KV → 统一蒸馏为紧凑表示
```

### 学术空白
跨模态管线联合蒸馏 = 0篇

### 参考技术
- VoCo-LLaMA [CVPR 2025] — 跨模态蒸馏（视觉→语言，方法论参考）
- Distil-Whisper [2024] — ASR蒸馏（编码器→小模型）
- Activation Beacon [ICLR 2025] — 激活压缩（跨段中间表示压缩）
- Seamless [Meta 2023] — 统一语音翻译模型（跨段统一参考）

### 技术目标
通话全链路：ASR→LLM→TTS延迟<500ms（当前>1s），MOS≥4.0，WER<5%
